# H8562 — soft-alert шторм: flap grace + single-flight на отправителе, lookup + reconcile на приемнике

Шторм issues 21–23.11 (35 открытых с одним заголовком `[soft-alert] guards
6fd69840`) шел по цепочке: guards-проба сэмплирует `systemctl --failed` каждые
*/15, failing-юнит (`telegram-daily.service`) флапает в такт таймеру */10 —
на тиках :00/:30 он в состоянии activating и невидим → ложная зеленая проба →
`reportToTelegram` забывал LAST_SOFT_FP/AT → тик :15/:45 видел тот же
отпечаток как «новый класс» → webhook → n8n безусловно создавал issue
(корень проверен read-only на .92: 77 failed exits за 24 ч,
`reserve_exhausted`; отпечаток `sha256("guards/failed-units") = 6fd69840`).
Теперь: (1) зеленая проба не снимает активный soft-инцидент — закрывают
только N зеленых подряд (`CABINET_PROBE_SOFT_GREEN_GRACE_TICKS`, по умолчанию
2; сбой сбрасывает счетчик), (2) вся секция read→check→send→write под
flock-локом (`CABINET_PROBE_SOFT_LOCK_WAIT_SECONDS`, 10 с; занятый лок =
тишина тика — перекрывающиеся пробы не читают «новый» отпечаток дважды;
сломанный лок fail-open), (3) n8n-экспорт: GitHub search по точному
заголовку до create, повторная доставка дописывается комментарием в открытый
issue, после create — reconcile по минимальному номеру (свежий дубль
комментируется и закрывает ровно сам себя; оба порядка гонки сходятся).
`SoftFailureFingerprint` уже нормализует волатильность (H2335/H3227) — класс
стабилен, расширять его не нужно; hard fuses, failed-unit детекция и
critical-ветка не тронуты. Воркараунд webhook-only-режима (без TG-токена
green-ветка не достигается) — прежний, отмечен в PR. Тесты: flap
(зелень-сбой-зелень-сбой молчит; устойчивая зелень закрывает; возврат класса
= одна новая тревога), single-flight (webhook уходит под локом), busy-skip
(занятый лок = нет отправки), обновлен ollama-tunnel тест (две зеленых
пробы), контракт n8n-экспорта (5 кейсов).

## v2 (23-11-2026, после independent review FAIL)

Independent review (23-11-2026) дал FAIL приемнику: обе конкурентные
доставки «не находили» issue через search, обе создавали, а НЕМЕДЛЕННЫЙ
search-reconcile из-за лага индекса видел только свой свежий issue —
предикат «есть открытый с меньшим номером» не срабатывал ни у кого, дубли
оставались; retry/durable-пути в экспорте не было, а single-flight
отправителя не сериализует запросы из других путей n8n. Сценарий «тот же
отпечаток сходится, другой открывает свой» из PR #4481 не проходил.

Рework приемника (та же цель, другой источник истины):

1. **Лист вместо поиска**: все чтения — строго консистентный REST-лист
   `GET /repos/…/issues?state=open&labels=ops-soft-alert&sort=created&direction=desc&per_page=100`,
   ни одного обращения к `/search/issues`. Метка — контракт issue; окно
   100 свежих (бэклог 49 влезает) — честно задокументировано.
2. **Один источник заголовка**: `expected_title` строит Code-узел
   «Match exact title»; create и reconcile читают его оттуда — дедуп-фраза
   и заголовок не могут разъехаться (у v1 было два независимых выражения).
3. **Reconcile по минимальному номеру над листом**: номера выдаются
   последовательно в момент create, лист консистентен → создавший старший
   номер ВСЕГДА видит младший при своем post-create списке и закрывает
   ровно себя. Все порядки гонки сходятся без ретраев.
4. **Durable sweep (раз в 6 ч)**: плановая группировка открытых
   ops-soft-alert issues по точному заголовку, выживает минимальный номер.
   Сходится из любого бэклога (первый проход после импорта закроет 46
   дублей шторма 21–23.11 — ожидаемый всплеск close-уведомлений), не
   зависит от индекса и от доставок, умерших посреди выполнения. PR и
   посторонние issues не тронуты (фильтр `pull_request` + метка).

Failed-unit детекция сохранена (failures/playbook/ssh-предложение в теле
issue, failures в комментариях повторов), секреты — на env, токенов в
экспорте нет. Тесты: контракт экспорта переписан (6 кейсов: отсутствие
`/search/issues`, контракт листа, lookup-before-create, close-ровно-себя,
один источник заголовка, sweep, секреты) + новый mocked-runner replay
`N8nSoftAlertWorkflowReplayTest` (6 кейсов, 298 утверждений суммарно):
все 6 порядков create/reconcile двух конкурентных доставок сходятся в один
issue под задержанной видимостью поиска (мок: лист консистентен, индекс
лагает), ноль обращений к индексу; отдельный новый отпечаток открывает
свой issue; неверный секрет → 401 без обращений к GitHub; sweep гасит
бэклог 35/7/7, выживает минимальный номер; PR с тем же заголовком
игнорируется. Расхождение search-дизайна воспроизведено моком и оставлено
как документация дефекта. Отправитель (`ProbeCabinetHealth`,
`SoftFailureFingerprint`) не тронут — `CabinetProbeTest` 28/96 зеленые.

## v3 (23-11-2026, follow-up independent review: три transport/logic-находки)

Второй independent review (вечер 23-11, `$TEMP/opencode/h8562-probe/
codex-independent-review.txt`) проверил экспорт исполнением точного JS и дал
три находки поверх v2:

1. **alwaysOutputData отсутствовал на initial HTTP list** — n8n не дает
   выхода у HTTP-узла на пустом массиве, поэтому на genuinely пустом борде
   «Match exact title» не исполнялся и ПЕРВЫЙ issue нового отпечатка никогда
   не создавался (тихая потеря доставки). Флаг Always Output Data (n8n node
   setting) поставлен на все три list-узла: пустой массив отдает один пустой
   item, ветка create живет, первый issue создается.
2. **Пагинация отсутствовала** — все три чтения были ограничены первой
   сотней (`per_page=100`), канонический issue за пределами 100 был невидим
   lookup'у и sweep'у. Поставлена ПОДДЕРЖАННАЯ n8n-пагинация (cookbook
   «Get the next page by number using $pageCount»; схема сверена с исходником
   HttpRequestV3): Update a Parameter in Each Request, Query `page` =
   `{{ $pageCount + 1 }}`, Pagination Complete When: Response Is Empty
   (GitHub отдает bare top-level array), Limit 20 запросов, Interval 300 мс —
   те же страницы, на которые указывает Link rel=next.
3. **Коллизия 8-hex префикса** — два различных sha256 могут делить первые
   восемь hex, и дедуп по заголовку склеивал чужие классы отказов. Заголовок
   остался 8-hex (отображение + легаси-совместимость), но совпадение теперь
   требует ПОЛНЫЙ отпечаток из тела: структурный маркер
   `<!-- soft-alert-fingerprint:… -->`, который create пишет в каждый новый
   issue, с легаси-строкой `**Fingerprint:**` как фолбэком для pre-v3 issues.
   Sweep группирует по паре (заголовок + доказанный полный отпечаток);
   неоднозначные легаси (тело без доказуемого отпечатка) не матчатся и
   НИКОГДА не закрываются — легаси-безопасность миграции.

Сходимость отложенной видимости сохранена (все 6 порядков
create/reconcile конкурентных доставок сходятся в один issue, ноль обращений
к поисковому индексу); failed-unit детекция, контракт метки, PR-фильтр,
секреты на env — не тронуты. Clear rollout contract добавлен в
docs/ops/SOFT_ALERT_WEBHOOK.md §4 (owner steps: проверка легаси-тел до
импорта, re-import на .91, визуальная проверка Pagination + Always Output
Data после импорта, ожидания первого sweep, smoke, инварианты аудита).

Тесты: реплей дополнен честным транспортным моделированием (ноль items на
вход = узел не исполняется; пустой лист + alwaysOutputData = один пустой
item; пагинация по страницам до пустой) — `N8nSoftAlertWorkflowReplayTest`
6 (сходимость конкурентных доставок, шторм-бэклог на легаси-телах с
**Fingerprint:** строкой) + новый класс `N8nSoftAlertWorkflowReviewReplayTest`
4 (пустой борд → первый issue создается; канонический за пределами сотни
виден lookup'у и sweep'у; коллизионный 8-hex не склеивается и не
закрывается; неоднозначные легаси не матчатся и не закрываются), контракт
`N8nSoftAlertWorkflowContractTest` 9 (3 новых: alwaysOutputData, схема
пагинации, полный отпечаток), новый `N8nSoftAlertWorkflowJsTest` исполняет
НАСТОЯЩИЙ JavaScript Code-узлов через node (tests/Support/N8n/
soft_alert_js_probe.cjs, 11 проверок; пропуск без node). Итог: 20 passed /
434 assertions + `CabinetProbeTest` 28/96, Pint чист; экспорт ужат до
19 941 Б под token-size gate без его обхода. Не деплоено, прод-вызовов
не было.
