# H4858: OOM-гард сборки ревью-PDF домашек пересажен на main-овую реализацию — пред-декодная оценка памяти, jpeg DCT-хинт и страница-заглушка вместо 500 (DeepSeek 4 Flash `deepseek-v4-flash`, 15-09-2026)

`app/Services/HomeworkImagePdfService.php` на main был **переписан** (`normalizeToDompdfImage` → `dataUriFor` → `downscaleGd`), и вместе с переписью потерялся единственный барьер, который держал POST сдачи: гард **до** декодирования. `max_edge_px`/`jpeg_quality` ужимают кадр уже после `imagecreatefromstring()`/`readImageBlob()`, то есть ровно в тот момент, когда память под полноразмерный декод (снимок айфона 4032×3024 — это ~42 МБ в dompdf плюс ~7,4 МБ base64-строки на страницу) уже выделена. Исчерпание памяти — фатальная ошибка PHP, её не ловит `try/catch`, поэтому `rebuildQuietly()` не срабатывает: падал весь POST, студент получал 500 на уже сохранённой в базе работе, а `notifyTeacher()` за сборкой не выполнялся. Ветка `fix/homework-pdf-oom` (PR #1766, [карта расхождений](https://github.com/gasyoun/Systema-Sanscriticum/pull/1766#issuecomment-5668387083)) несла настоящий фикс; здесь он пересажен на текущую реализацию main, а не влит как есть.

- **Гард стоит ДО декода.** Габариты читаются из заголовка (`getimagesizefromstring`, для heic — `Imagick::pingImageBlob`), затем [`RasterImageMemory::fits()`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Support/RasterImageMemory.php) сравнивает оценку декода с остатком `memory_limit` и ценой пикселя конкретного движка (Imagick Q16 — 8 байт с запасом, GD — 5). Не влезает — кадр вообще не открывается.
- **Сентинел `PAGE_TOO_LARGE` + страница-заглушка.** Неподъёмный файл больше не «нечитаемо» и не «вклеить как есть»: `rebuild()` собирает страницу-заглушку «Страница пропущена: файл слишком большой для сборки PDF. Откройте оригинал в кабинете», пишет `warning` с `file_id`/`mime`/`size` и **выживает** — проверяющий видит, что файл есть, а не гадает, почему страниц меньше, чем файлов. Вид [`pdf/homework-images.blade.php`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/resources/views/pdf/homework-images.blade.php) получил ветку `skipped` (без неё заглушка падала бы на отсутствующем ключе `data_uri`).
- **jpeg DCT-хинт — только когда он уменьшает.** `Imagick::setOption('jpeg:size', 2×maxEdge)` заставляет libjpeg декодировать сразу в уменьшенном DCT-масштабе, и память считается по уменьшенным габаритам. Ставится лишь при `max(w,h) > 2×max_edge`: на маленьком JPEG libjpeg масштабирует по хинту **вверх** (640×480 декодировался в 1280×960 — это ловит CI-тест `small_image_keeps_its_dimensions`), а при неизвестных габаритах апскейлом рисковать нельзя.
- **Никакого «отдать как есть».** Прежний passthrough сырых байт для кадров, которые не прочитали ни Imagick, ни GD, — тот самый путь, что раздувал сборку. Крупный нечитаемый кадр → `PAGE_TOO_LARGE`, мелкий нечитаемый → `null` (пропуск). Потолки ImageMagick (`RESOURCETYPE_MEMORY` 64 МБ / `MAP` 128 МБ) уводят переполнение в дисковый pixel-cache вместо OOM процесса; прозрачность ложится на белый, EXIF-поворот работает и в GD-ветке.
- **Сигнатуры для воркера не тронуты:** `rebuild()`/`rebuildQuietly()` остались как есть, `HomeworkService::queueImagesPdfRebuild → BuildHomeworkImagesPdfJob → rebuild()` не менялся, потолок `max_pages` и его warning сохранены.
- **Тесты:** новый [`HomeworkImagePdfDownscaleTest`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/tests/Feature/HomeworkImagePdfDownscaleTest.php) (6 тестов: даунскейл с сохранением пропорций, jpeg не проходит нетронутым, мелкая картинка не растёт, прозрачный PNG на белом, заглушка + `warning` + выживание сборки, сквозная сдача двух крупных фото через очередь) — гард-кейс использует крафтовый PNG-заголовок 60000×60000 без пиксельных данных, поэтому гигабайты ему не нужны. Два main-овых теста, ходившие в приватный `normalizeToDompdfImage` через рефлексию, переведены на публичный шов `convertToPdfJpeg()`.
