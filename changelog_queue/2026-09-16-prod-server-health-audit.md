# Аудит здоровья прод-сервера .92: починен отказавший юнит word-of-day, задокументированы две находки по бэкапам (Opus 5 `claude-opus-5`, 16-09-2026)

Полный read-only обход прод-контейнера samskrte.ru (193.232.229.92) по запросу «improve server health», без указания класса. Отчёт: [docs/AUDIT_PROD_SERVER_HEALTH_16-09-2026.md](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/AUDIT_PROD_SERVER_HEALTH_16-09-2026.md).

- **Починен единственный живой отказ: `samudra-word-of-day.service` держал весь systemd в состоянии `degraded`.** Каталог `/opt/samudra/repo/web/app/data` был `root:root drwxr-xr-x`, а юнит выполняется от пользователя `samudra` — отсюда `PermissionError: [Errno 13]` при записи `word_of_day_current.json`. Выставлено `root:samudra drwxrwsr-x` (setgid, наименьшая привилегия: файл пула 9.7 МБ остаётся `root:root` и только на чтение), юнит перезапущен. После: `Result=success`, слово дня сгенерировано, `systemctl is-system-running` → **`running`**, отказавших юнитов 0.
- **Ловушка, которую стоит запомнить:** `ReadWritePaths` в юните этот каталог разрешал — отказ был не в systemd-песочнице, а в обычных правах POSIX. При `Errno 13` в отвержённом юните первым делом смотрят `ReadWritePaths`, хотя смотреть надо `ls -ld`.
- **Правка намеренно временная.** Ветка `h4955-runtime-path-fix` (коммит `2e48eb5`, другая сессия в полёте) уносит рантайм-запись из git-подконтрольного дерева вообще; `deploy/samudra-word-of-day.service` в SamudraManthanam этим проходом не трогался, чтобы не столкнуться с работой в полёте.
- **Две незакрытые находки по резервным копиям → [H4979](https://github.com/gasyoun/Uprava/blob/main/handoffs/H4979-Sonnet_Systema-Sanscriticum_restic-sftp-lock-leak-and-single-destination_16.09.26.md).** (1) restic не может удалять свои замки на SFTP-приёмнике `.91` — **156** строк `Remove(<lock/…>) failed: permission denied` в логе и **5** прогонов с `overall_rc=1` за 7 суток; замки от успешного прогона 07:34 лежали в `/systema/locks` ещё в 08:20. Оповещение работает (`telegram=delivered`) — не хватает только ремедиации. (2) Второй приёмник не заведён: каждый прогон пишет `lane=s3 dest=s3 status=SKIP reason=no-/root/.restic-s3.env`, то есть **офсайт-копии сегодня нет** — источник `.92` и приёмник `.91` на одной локальной сети.
- **Остальное измерено живыми пробами и здорово:** диск 24% из 147 ГБ, память 2.6 из 16 ГБ, 0 обновлений безопасности в очереди, nginx 2 ошибки 5xx из 16 968 запросов за сутки, MariaDB 0 медленных запросов за 18.8 сут, 4 из 4 TLS-сертификатов валидны, fail2ban активен, 0 ошибок ядра и OOM за 7 дней.
- **Открыто для человека:** `/var/run/reboot-required` просит перезагрузку под новое ядро `6.12.107+deb13-rt-amd64` (работает `6.17.9-1-pve`, аптайм 48 суток, простой ~1–2 мин). Ничего не блокирует — решение за человеком.
