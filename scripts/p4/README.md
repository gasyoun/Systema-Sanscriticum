# P4 readiness reference harness

_Создано: 25-10-2026 · Обновлено: 25-10-2026_

Это **не** продакшн-миграция P4 и не вторая бухгалтерская книга. Это report-only эталонная модель проверок, которые должна выдержать миграция H5446, запускаемая на изолированной SQLite. Прод не читается и не пишется: вход — только снимок, снятый read-only, и манифест, собранный из него.

## Зачем отдельная модель

В прод-схеме P4 ещё нет: получателя (ИП) у движения, начальных остатков, снимка миграции, журнала применения. Добавлять их в прод — работа самого H5446, а не подготовка. Поэтому пакет фиксирует инварианты, которые реальная реализация обязана портировать:

1. отпечаток dry-run обязан совпасть при apply — изменение входа после dry-run отвергается;
2. новые платежи между снимком и apply не применяются молча;
3. повтор доказательства — типизированное исключение, а не второе движение;
4. получатель в перекрытии D22 (период B) требует первичного доказательства; дата недостаточна;
5. контроль идёт по bucket `получатель × период × валюта` и по обязательствам, поэтому две взаимно компенсирующие ошибки не прячутся за равным большим итогом;
6. apply идемпотентен при повторе и возобновляем после прерывания;
7. типизированное исключение по умолчанию **не** допустимо для переключения.

## Запуск

```bash
python3 -m unittest discover -s tests/p4 -v

python3 scripts/p4/readiness.py plan \
  --snapshot /path/to/p4_snapshot.json \
  --p1 /path/to/p1_backfill.json \
  --out /tmp/manifest.json

python3 scripts/p4/readiness.py apply --manifest /tmp/manifest.json --db /tmp/p4.sqlite
python3 scripts/p4/readiness.py apply --manifest /tmp/manifest.json --db /tmp/p4.sqlite --apply --run-id r1
python3 scripts/p4/readiness.py verify --manifest /tmp/manifest.json --db /tmp/p4.sqlite
```

`apply` без `--apply` — dry-run: ничего не пишет, печатает `writes: 0`.

## Что проверяет verify

- `fingerprint_matches` — вход не изменился после dry-run;
- `grand_total_matches` — большой итог;
- `recipient_period_currency_buckets_match` — каждый bucket; ловит подмену получателя и компенсирующие ошибки;
- `obligation_allocations_match` — распределения сходятся с движениями;
- `no_non_admissible_exceptions` — типизированное исключение не PASS по умолчанию;
- `every_manifest_row_accounted_for` — каждая строка манифеста применена или объяснена исключением;
- `unallocated_residue_visible` — нераспределённый остаток виден, не обнуляется.

## Чего здесь нет

- никакого подключения к MySQL/проду;
- никакой записи `money_movements`/`allocations`/`obligations` в прод;
- никакой реконструкции обычной закрытой истории (D3);
- никакой конвертации валют: иностранные суммы — memo;
- никакого UI/читателей: переключение чтений — отдельный шаг H5446.

## Требования к реальной реализации H5446

1. Портировать эти семь проверок в Laravel/PHP и прогнать на MariaDB 11.8 (прод-движок), не только SQLite.
2. Добавить в схему получателя/ИП и `recipient_evidence`; в период B запретить запись без доказательства.
3. Хранить `snapshot_fingerprint` и отпечаток apply; отказ при несовпадении.
4. Считать контрольные суммы по bucket, а не только по большому итогу; публиковать их до/после.
5. Сделать batch-commit и resume; проверить kill -9 посередине на копии прод-БД.
6. Не считать `admissible` по умолчанию; каждое исключение — с основанием, автором и решением.
