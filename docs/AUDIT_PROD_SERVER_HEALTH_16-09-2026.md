## 1. Что было сломано и что починено

**`samudra-word-of-day.service` падал, и из-за него весь systemd стоял в
состоянии `degraded`.**

Двойной отказ в течение девяти минут 16-09-2026, оба — последствия выкладки H4955:

| Время (UTC) | Код | Симптом | Причина |
|---|---|---|---|
| 07:58:57 | `226/NAMESPACE` | `Failed to set up mount namespacing: /opt/samudra/data: No such file or directory` | юнит из репозитория ссылался на `/opt/samudra/data`, которого на проде нет — реальный каталог называется `/opt/samudra/db` |
| 08:06:20 | `1/FAILURE` | `PermissionError: [Errno 13] Permission denied: '/opt/samudra/repo/web/app/data/word_of_day_current.json'` | каталог был `root:root drwxr-xr-x`, а юнит выполняется от пользователя `samudra` |

Первый отказ кто-то уже пролечил руками, отредактировав юнит на проде в 08:06.
Второй остался — его и чинил этот проход.

**Важно: `ReadWritePaths` в юните каталог разрешал.** Ошибка была не в
systemd-песочнице, а в обычных POSIX-правах: `ProtectSystem=strict` открывает
путь на запись для юнита, но не выдаёт пользователю права, которых у него нет.
Это классическая ловушка — при `Errno 13` в отвержённом systemd-юните сначала
смотрят `ReadWritePaths`, хотя смотреть надо `ls -ld`.

**Применённое исправление** (наименьшая привилегия — файл пула остаётся
`root:root`, только на чтение для сервиса):

```sh
chgrp samudra /opt/samudra/repo/web/app/data
chmod 2775 /opt/samudra/repo/web/app/data   # setgid: новые файлы наследуют группу samudra
systemctl start samudra-word-of-day.service
```

**Проверено после**: `Result=success`, `ExecMainStatus=0`, сгенерировано слово дня
`मन्त्राधिराज mantrādhirāja`, файл `word_of_day_current.json` создан от
`samudra:samudra`, `systemctl is-system-running` → **`running`**, отказавших
юнитов 0. Следующий штатный запуск — 17-09-2026 00:05 UTC.

**Известный задокументированный пробел, не дефект**: `word_of_day_post.py`
печатает `TELEGRAM_WOD_BOT_TOKEN/TELEGRAM_WOD_CHAT_ID not set` — канал
samskrtam.ru ещё не заведён, публикация не происходит намеренно (H4955).

### Почему эта правка временная

Другая сессия уже держит в работе архитектурно верное исправление: ветка
`h4955-runtime-path-fix` (коммит `2e48eb5`, worktree `SamudraManthanam-h4955-18152`)
уносит рантайм-запись **из git-подконтрольного дерева репозитория вообще** —
в юните остаётся `ReadWritePaths=/opt/samudra/db`. После её выкладки
`web/app/data` перестаёт быть местом записи, и права, выставленные выше,
становятся безвредным остатком. Файл `deploy/samudra-word-of-day.service` в
SamudraManthanam этим проходом намеренно **не** трогался, чтобы не столкнуться
с работой в полёте.

## 3. Незакрытые находки — резервные копии

Обе ведёт [H4979](https://github.com/gasyoun/Uprava/blob/main/handoffs/H4979-Sonnet_Systema-Sanscriticum_restic-sftp-lock-leak-and-single-destination_16.09.26.md).

### 3.1 Утечка замков restic и ~5 провалов в неделю

`/var/log/restic-backup.log` содержит **156** строк
`Remove(<lock/…>) failed: … permission denied` по каталогу `/systema/locks` на
SFTP-приёмнике. За последние 7 суток **5** прогонов закончились `overall_rc=1`:
10-09 10:00, 13-09 06:06, 13-09 06:40, 14-09 06:05, 14-09 16:32 — каждый с
`sftp=FAIL` хотя бы по одной дорожке.

Замки действительно текут: два файла от успешного прогона 07:34 всё ещё лежали
в `/systema/locks` в 08:20 — через 46 минут после того, как прогон завершился.
Каталог `drwxrwxr-x` uid 999 gid 988, сами замки `-rw-------` того же
владельца, то есть их пишет сам подключающийся `restic-push`, но удалить не
может. Учётная запись — только SFTP (`This service allows sftp connections
only`), поэтому отказ формируется **на стороне `192.168.200.91`**: конфигурация
`Match`/`internal-sftp` в sshd или деталь chroot/владения, а не вызывающая
сторона на `.92`.

**Оповещение при этом работает** — каждый провал отправил
`alert kind=run_fail:… telegram=delivered`. Не хватает только ремедиации, что
ровно соответствует классу №9 из
[INCIDENT_LEDGER_SYSTEMA_UPTIME.md](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/INCIDENT_LEDGER_SYSTEMA_UPTIME.md):
«обнаружение мгновенное, ремедиации нет».

### 3.2 Второй приёмник не заведён — офсайт-копии нет

Каждый прогон пишет `lane=s3 dest=s3 status=SKIP reason=no-/root/.restic-s3.env`.
Скрипт `/usr/local/sbin/systema-restic-run.sh` спроектирован на два приёмника,
но живёт один: SFTP на `192.168.200.91`. Источник `.92` и приёмник `.91` — на
одной локальной сети и одном гипервизоре, то есть **офсайт-копии сегодня не
существует**, и один отказ площадки уносит обе копии сразу.

Заведение ключей S3 — действие человека; агент учётные данные не трогает.
