## Известные ограничения / оговорки

- Спека опирается на решение MG по модели «один реальный платёж + нулевые sibling-строки доступа»; при пересмотре этого решения #1–#2 теряют силу.
- Границы Phase 2 (промокод/лояльность на рассрочку, частичная оплата плоского блока, смена графика студентом) заданы осознанно — документ их не покрывает по замыслу, а не по недоработке.
- Числовые дефолты (`DEBT_RESCHEDULE_MAX_DAYS=14`, допуск 1 ₽) могут разойтись с фактической конфигурацией окружения — метадок их не отслеживает.

## Назначение / известное неверное употребление

- **Употреблять** как ТЗ для реализующей сессии и как чек-лист приёмки Phase 2.
- **Не употреблять** как описание уже поставленного функционала: на дату метадока это спека к реализации, а не отчёт о внедрённом. Статус «реализовано» подтверждается только мержем соответствующего PR и обновлённым `debtors-manual`.

## План сопровождения и вывода из эксплуатации

- Обновлять при изменении бизнес-границ Phase 2 или модели sibling-строк доступа.
- По завершении реализации: пометить строки бэклога done с ссылкой на PR, обновить sibling-спеку Phase 1 и `debtors-manual`.
- Вывод из эксплуатации — когда весь функционал Phase 2 внедрён и задокументирован в `debtors-manual`; тогда спеку архивировать, а метадок пометить `superseded` с указанием мануала-преемника.
