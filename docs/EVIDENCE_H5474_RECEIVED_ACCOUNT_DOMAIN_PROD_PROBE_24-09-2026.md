# H5474 — `received_account='teacher'`: прод-зонд, разбор последствий и решение для MG

_Created: 24-09-2026 · Last updated: 25-09-2026_

Зонд только на чтение, прод (`193.232.229.92`, `/var/www/html`), 24-09-2026.
Персональных данных нет: только id, суммы, валюта (152-ФЗ).

## 1. Что на проде

Перепись домена колонки:

| `received_account` | строк |
|---|---|
| `school` | 9442 |
| `teacher` | 10 |
| `teacher_personal` | **0** |

Валидные значения — `school` и `teacher_personal`
([`Payment::RECEIVED_SCHOOL` / `RECEIVED_TEACHER`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Models/Payment.php)).
Значение `teacher` не пишет ни одна строка кода репозитория — источник сырой SQL или
tinker. **Легальных прямых платежей на проде нет ни одного:** все 10 «прямых» строк
лежат в невалидном значении, то есть механизм `directReceiptsForTeacher()` за всё
время ни разу не сработал на реальных данных.

## 3. Главная находка: получатель денег НЕ ведёт эти курсы

| | |
|---|---|
| Получатель денег | преподаватель **#3**, `payout_currency=EUR` |
| Курсы, которые #3 ведёт (`allTaughtCourses`) | **266, 334** |
| Курсы этих десяти строк | **364, 367, 399** |

Владельцы затронутых курсов — другие люди:

| курс | преподаватель | ставка |
|---|---|---|
| 364 | #1 | 20 % |
| 367 | #20 | 30 % |
| 399 | #1 | 20 % |

[`TeacherSalaryService::directReceiptsForTeacher()`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Services/TeacherSalaryService.php)
перебирает **только `allTaughtCourses()` получателя**. Курсов 364/367/399 там нет,
поэтому зачёт по этим строкам не состоится ни при каком значении `received_account`.

Проверка на «уже удержали руками» — отрицательная:
`teacher_payouts` преподавателя #3 (50 строк) не содержат ни одной ссылки на эти
десять id, ни одного `breakdown` со словом `direct`, ни одной отрицательной суммы,
ни одного комментария про удержание. **Refute-условие из H5474 не выполнилось:
вручную эти строки не реконсилированы.**

## 4. Почему наивный релейбл в `teacher_personal` — дефект

Сегодня `'teacher' !== RECEIVED_TEACHER`, поэтому
[`isCourseRevenuePayment()`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Services/TeacherSalaryService.php)
**считает эти строки выручкой курса**, и преподаватели курсов уже получили с них
свой процент — начисление верное, курс вели они.

Перевод в `teacher_personal` выбросил бы строки из выручки:

| курс | «teacher»-сумма, ₽ | ставка | потеря преподавателя, ₽ |
|---|---|---|---|
| 364 | 43 860 | 20 % | 8 772 (#1) |
| 367 | 18 180 | 30 % | 5 454 (#20) |
| 399 | 7 060 | 20 % | 1 412 (#1) |
| | | | **15 638** |

…и при этом **не вернул бы ни копейки** с держателя денег (§3). То есть наивный
релейбл делает хуже обеим сторонам сразу — ровно то, чего MG не хочет
(«teachers should get all they deserve, otherwise they will leave us»).

**Поэтому дефолт команды — `school`.** Он не меняет ни одного начисления:
пер-блочный калькулятор уже считал эти строки выручкой, а сводные читатели
(`scopeSchoolReceived()`: RevenueRecognition, FinanceCockpit, SafeWithdrawal,
PayoutForecast, PayrollContour, `blockGroupRevenueDetail`, PayoutRunService)
наконец начинают видеть то же самое. Разъезд «сводка vs калькулятор» на 69 100 ₽
закрывается в сторону калькулятора, то есть в сторону уже выплаченного.

Обязательство преподавателя #3 вернуть 685 EUR в кассу — **отдельный вопрос
взаиморасчёта**, а не признак `received_account`. Решать его перекраской строки
нельзя: `MutualSettlementService::tuitionFor()` считает человека плательщиком-учеником,
а не держателем чужих денег.

## 5. Решение, которое должен принять MG

Вопрос: **какую долю прямого платежа получает преподаватель?**

Пусть преподаватель со ставкой p собрал напрямую X, а прочая выручка курса = R.

| модель | к выплате | итог у преподавателя | доля школы от X |
|---|---|---|---|
| **Сегодняшняя формула** (исключить из выручки + вычесть номинал) | p·R − X | p·R | 100 % |
| **Если бы X прошёл через кассу** | p·(R+X) | p·R + p·X | (1−p) |
| **Что обещает [docs/direct-teacher-receipts.md:19-22](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/direct-teacher-receipts.md)** («школа НЕ берёт свою долю, преподаватель оставляет себе полный номинал») | p·R | p·R + X | 0 % |

Три числа расходятся. На ставке 20 % и X = 100 000 ₽ преподаватель получает
итогом либо ровно `p·R` (формула), либо `p·R + 20 000` (касса), либо
`p·R + 100 000` (док). Формула и док противоречат друг другу на весь номинал X,
формула и касса — на p·X.

**Рекомендация:** привести **док к формуле**, а не наоборот, но с одной поправкой в
пользу преподавателя — считать прямой платёж выручкой курса и вычитать номинал
(средняя строка таблицы). Тогда преподаватель получает `p·R + p·X`: ровно то же,
что если бы деньги прошли через кассу, то есть способ получения денег перестаёт
влиять на его заработок. Это и есть «teachers get all they deserve» без подарка
школе и без подарка преподавателю.

**Что изменится, если принять:** `blockPayoutTotal` начнёт считать прямые платежи
выручкой; каждый преподаватель, бравший прямые оплаты, получит +p·X за период.
На сегодняшних данных это 0 ₽ — легальных `teacher_personal` строк на проде нет
(§1), так что менять арифметику можно без перерасчёта прошлого.

**Что будет, если не принимать:** формула остаётся, но
[docs/direct-teacher-receipts.md](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/direct-teacher-receipts.md)
правится в ту же сторону — обещание «преподаватель оставляет себе полный номинал»
из него уходит, потому что код так не делает и никогда не делал.

**Арифметику выплат без ответа MG этот PR не трогает** (шаг 2 H5474).
