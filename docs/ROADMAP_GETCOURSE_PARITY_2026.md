## 2. Три ставки квартала

1. **Вебинар-аналитику довести до 100% и застраховать уход с Zoom** — самый дешевый и самый близкий к завершению домен; страховка = BigBlueButton (руллинг §5.1).
2. **CRM поднять до сущности `Deal` с канбаном** — ежедневный инструмент менеджера, окупается при ручных продажах быстрее квизов (руллинг §5.6 поднял CRM выше маркетинга).
3. **Ввести движок квизов с гейтингом и транслит-aware проверкой** — единственный полностью отсутствующий у getcourse-паритета функционал; транслит-aware проверка (IAST↔деванагари↔кириллица) — то, чего у getcourse нет и не будет.

Реалистично: за квартал закрываются вебинар-домен целиком, ядро CRM (`Deal`+канбан+атрибуция) и ядро квизов (движок + гейтинг за флагом); маркетинг-ядро (сегменты+роутер) стартует в хвосте квартала, тяжелые хвосты (кампании с трекингом, нативные цепочки, полное BBB-развертывание) уезжают в Q4 — помечены `Later`.

## 3. Тикеты

Оценка каждого: **E** усилие (S/M/L) · **V** ценность · **R** реюз · **Risk**. Все за фича-флагом (`config/features.php`), watcher-safe сборка, аддитивные миграции — денежное ядро не трогаем.

### Домен B — Вебинар-аналитика + страховка ухода с Zoom (готовность высокая → делаем первым)

**GC-B1 · Авто-создание Zoom-встреч через API — 🔴 @DECIDE MG, НЕ реализовано (H553, 11-07-2026).** Тикет предполагал добавить `createMeeting()` и писать `zoom_join_url`/`zoom_start_url` при создании **каждого** `Schedule`. Прежде чем строить, `/prior-art` нашёл, что это уже существовало и было **сознательно удалено**: commit [`eda8059`](https://github.com/gasyoun/Systema-Sanscriticum/commit/eda8059e8ae16086ee0ef22f6b78c4a91def3b71) (27-06-2026, «учёт посещаемости Zoom-занятий под единую ссылку курса») переписал вебинар-подсистему под **единую постоянную Zoom-ссылку на курс** (`courses.zoom_link`/`zoom_meeting_id`, ручные встречи) и явно указывает в сообщении: «Чистка: убраны `ZoomService::createMeeting`, действие «Создать Zoom-встречу»» — т.е. по-schedule авто-создание уже пробовали и убрали, потому что не соответствует реальному процессу школы. Слепая реализация тикета как написано откатила бы этот шаг задним числом. **Нужен человек:** либо переподтвердить per-schedule авто-создание и объяснить, чем не устроила июньская модель «единая ссылка», либо закрыть/переформулировать тикет под единую-ссылку модель (например: авто-создание ОДНОЙ recurring-встречи на курс при первой генерации потока, а не на каждое занятие). До решения — не в скоупе. **E:S · V:M · R:высокий (OAuth готов) · Risk:низкий (но архитектурный конфликт) · flag:`zoom_auto_create`**

Флаг `attendance_dashboard`, выкл по умолчанию. **E:M · V:высокий · R:высокий · Risk:низкий · flag:`attendance_dashboard`**

**GC-B3 · Провайдер-абстракция вебинаров (страховка ухода Zoom) — целевой драйвер BigBlueButton (решено §5.1)** — сейчас Zoom вшит везде (колонки БД `zoom_*`, [`ZoomWebhookController`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Http/Controllers/Webhooks/ZoomWebhookController.php), сервис). ### Домен C — CRM-воронка (поднят в приоритете руллингом §5.6 — ядро сразу после домена B)

**GC-C1 · Сущность `Deal` + канбан стадий (решено §5.4: отдельная сущность, НЕ расширение `Lead`)** — [`Lead`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Models/Lead.php) остается слоем «человек/интерес» (5 статусов, авто-конверт на оплате — не трогаем); НОВАЯ модель `Deal` = конкретная потенциальная продажа (FK `lead_id`/`user_id`/`course_id`, сумма, настраиваемые стадии в данных, `assigned_to`, история переходов). У человека может быть несколько сделок (второй курс, апгрейд тарифа) — этого `Lead` в одиночку не выражает. Канбан drag-drop — реюз уже подключенного пакета `mokhosh/filament-kanban` (сидит в composer, использован марафонской доской). Мост: успешный `Payment` закрывает соответствующий `Deal` (та же наблюдательная точка `PaymentObserver`, аддитивно). Миграция данных: открытые `Lead` НЕ конвертируются массово — `Deal` заводится вперед для новых продаж, старые дожимаются как раньше. **E:L (был M — сущность дороже расширения) · V:M · R:средний (kanban-пакет + PaymentObserver готовы) · Risk:средний · flag:`crm_pipeline_board`**

**GC-C2 · Атрибуция продаж по менеджерам** — `Lead.assigned_to` есть, но ни один отчет не атрибутирует конверсию/выручку менеджеру ([`OrderPaymentConversionService`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Services/Reports/OrderPaymentConversionService.php) ломает только по курсу/каналу). Добавить разбивку по `assigned_to` (после GC-C1 — по `Deal.assigned_to`). Filament-страница. **E:S · V:M · R:высокий · Risk:низкий · flag:`manager_sales_report`**

**GC-C3 · Объект-задача менеджеру** `Next` — промоутить поля `next_contact_at`/`assigned_to` в реальную модель `FollowUpTask` (due/done/тип), кормит [`WorkQueueReport`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Services/WorkQueueReport.php); включить флаг `crm_reminders`. ## 4. Рекомендуемая последовательность Q3 2026 (Now / Next / Later)

Порядок закреплен рулингом §5.6: дешевые вебинарные победы → CRM → квизы → маркетинг.

**Now** (быстрые победы + CRM-ядро): GC-B1 → GC-B2 → GC-C1 (Deal+канбан) → GC-C2
**Next** (квизы одним потоком + фундамент маркетинга): GC-D1 → GC-D3 → GC-D2 → GC-D4 → GC-C3 → GC-A1 → GC-A2
**Later** (тяжелые хвосты, вероятно Q4): GC-A3 → GC-A4 (гибрид) → GC-B3 (шов + BBB-скелет; BBB-сервер — инфра Q4)

Логика: сперва добить почти-готовый вебинар-домен (B1/B2 — минимум усилий, максимум ценности); затем `Deal`+канбан — ежедневный инструмент менеджера при ручных продажах (окупается быстрее квизов); квизовый поток D1→D3 идет неразрывно (движок сразу с гейтингом, транслит-aware с первого релиза); маркетинг-фундамент (A1 сегменты → A2 роутер) — хвост квартала, на него в Q4 сядут кампании A3 и гибридные цепочки A4.
