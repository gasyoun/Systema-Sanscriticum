Персональные данные не приводятся: курс публичный, поэтому в тексте только агрегаты,

## Кратко

Постановка волны 3 («на 27 уроков курсов 332/375 заведено 2 расписания и `webinar_attendances`
пуст») **не подтвердилась ни в одной из трёх частей**. Таблица не пуста, расписаний не два,
и сбор посещаемости работает. Ломается следующий шаг — **сопоставление участника Zoom с
пользователем платформы**, и именно он обнуляет плашку покрытия.

| Утверждение волны 3 | Что на самом деле (31-08-2026) |
|---|---|
| `webinar_attendances` пуст | 1218 строк, 67 занятий, 11 курсов, с 25-03-2026 по 30-08-2026 |
| у 332/375 заведено 2 расписания | у 375 — **14** занятий, у 332 — **ноль** |
| 27 уроков двух курсов | 332: 15 уроков, 0 занятий; 375: 12 уроков, 14 занятий |
| сбор посещаемости сломан | сбор работает: у 375 — 229 строк на 13 из 14 занятий |

## Причина 1 (главная) — посещаемость собирается, но ни к кому не привязывается

Плашка покрытия на экране «Потоки курса» считает **пользователей**, а не строки:
[`CourseStreamComparisonReport::attendance()`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Services/CourseStreamComparisonReport.php)
берёт `webinar_attendances` через `whereIn('user_id', $ids)`. Замер по семье 332/375/424:

```
family_payers      71
covered_users      17   (покрытие 23,9 %)
lesson_view_users  17
webinar_users       0
```

**Ноль.** Все 23,9 % покрытия дают просмотры записей; посещаемость вебинаров не добавляет
к плашке ни одного человека — при 229 собранных строках на курсе 375. По курсам:
332 — 52 плательщика, 0 по вебинарам, 10 по просмотрам; 375 — 28 плательщиков, 0 по
вебинарам, 12 по просмотрам.

Почему так. Единственный мост «участник Zoom → пользователь» в
[`AttendanceRecorder`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Services/Zoom/AttendanceRecorder.php)
— почта: `User::where('email', User::normalizeEmail($email))`. А Zoom отдаёт `user_email`
только для участников, залогиненных в аккаунт того же Zoom-аккаунта. По всей базе:

| Показатель | Значение |
|---|---|
| строк посещаемости всего | 1218 |
| из них с непустой почтой | 52 (**4,3 %**) |
| из них с проставленным `user_id` | 48 |
| строк, восстановимых по почте без учёта регистра | 1 |
| строк, восстановимых по точному совпадению имени | **0** |
| плательщиков 375, узнанных по имени среди участников | **0** |

То есть **96 % строк в принципе не могут получить `user_id`** — почты в источнике нет.
Запасной путь «по имени» не работает: экранные имена в Zoom — это транслитерации,
имя устройства (`iPhone`) и номера телефонов, они не равны `users.name` ни в одном случае
из 1218. Это не дефект кода, а свойство источника: **чинится не сбором, а идентификацией**.

Починка идентификации — это **UPDATE уже существующих строк**, что волне 3 прямо запрещено
(«только вставки»), и одновременно решение об атрибуции конкретного человека. Поэтому она
вынесена из этой волны целиком, см. «Что осталось человеку».

## Причина 2 — у курса 332 нет ни одного занятия, привязывать посещаемость не к чему

- `schedules` для курса 332 — **0 строк**.
- Вся таблица `schedules` начинается с **25-03-2026** (987 строк, самая ранняя — 25-03-2026).
- Платежи по курсу 332 идут с **05-09-2025**, все 15 уроков заведены задним числом
  01-04-2026 одной датой-заглушкой `2025-10-08`.
- `course_blocks` курса 332: четыре блока, у всех `starts_at`/`ends_at` = NULL.

Первый поток (осень 2025 — зима 2026) прошёл **до того, как в системе появились занятия
вообще**. Посещаемость не «потерялась» — её негде было хранить.

## Причина 3 — «два расписания» это две генерации строк, а не два параллельных расписания

У курса 375 действительно два семейства заголовков, но даты у них **не пересекаются**:

- ID 1565–1576 — «Кашмирский шиваизм (2 поток, 2026) — занятие DD.MM», 12 дат
  с 25-03-2026 по 08-07-2026;
- ID 643–644 — «Кашмирский шиваизм, часть 2 2026 (#15, 24.06.26)» и «(#16, 01.07.26)»,
  2 даты.

Итого 14 занятий, ни одного дубля по дате. Проблемная строка ровно одна: **занятие 643
(24-06-2026)** — у него `zoom_meeting_id` = NULL и 0 строк посещаемости.

## Резолв `zoom_meeting_id` из общей ссылки курса — проверен, работает

Волна 3 просила проверить эту цепочку. Проверено:

1. [`Course::setZoomLinkAttribute()`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Models/Course.php)
   вытаскивает `/j/{digits}` из `zoom_link` **при каждой записи**, поэтому состояние
   «ссылка есть, id нет» через модель недостижимо.
2. Курс 375: `zoom_meeting_id` заполнен, 13 из 14 занятий его унаследовали.
3. Курс 332: **нет ни ссылки, ни id** — ссылку в карточку курса просто никогда не вносили.
   Это и есть причина, по которой резолв «из общей ссылки» для него не срабатывает:
   резолвить не из чего.
4. Занятий с собственным `zoom_meeting_id` при пустом id курса в базе — 0.

Новая команда закрывает цепочку целиком: курс → ссылка курса → ссылка любого его занятия.

## Что Zoom ещё хранит — первый поток НЕ потерян на стороне Zoom

`past_meetings/{id}/instances` по общей комнате курса отдаёт **75 запусков начиная с
21-08-2025**, включая весь первый поток. Дневные будние запуски с реальной аудиторией:

| Период | Запусков | Участников на запуск |
|---|---|---|
| 17-09-2025 … 17-12-2025 | 13 | 18–48 |
| 01-01-2026 … 18-03-2026 | 9 | 12–23 |
| с 25-03-2026 (2-й поток) | 14 | 9–34 |

Плюс служебные запуски на 1 участника (host заглянул) и один вечерний воскресный запуск
15-02-2026 на 57 человек — по времени и дню недели это **не занятие курса**, а отдельное
мероприятие в той же комнате.

**Отсюда — граница возможного.** Данные за 2025 год у Zoom есть, но 22 подходящих запуска
против 16 уроков курса 332 означают, что часть запусков принадлежит другим активностям той
же личной комнаты. Разложить 22 запуска по 16 урокам — атрибуция, а не арифметика, и она
меняет помесячное признание зарплаты преподавателя (`schedules` кормит
`TeacherPayoutReconciliation`). Агент такое не решает: см. «Что осталось человеку».

## Что отгружено этой волной

[`attendance:backfill-streams`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Console/Commands/BackfillStreamAttendance.php)
— досбор `webinar_attendances` из Zoom Reports API, **только вставки**:

- запрет UPDATE/DELETE проверяется в рантайме
  ([`InsertOnlyGuard`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Support/InsertOnlyGuard.php)),
  а не только на ревью: запрещённый запрос роняет транзакцию до коммита;
- повторный прогон — no-op: существующая строка не переписывается даже при других данных
  в Reports API;
- занятия задним числом **не заводятся** — запуск Zoom привязывается только к уже
  существующему занятию на ту же календарную дату;
- `--min-participants` отсекает служебные запуски общей комнаты;
- отчёт всегда печатает обе стороны расхождения: занятия без источника в Zoom и запуски
  Zoom без занятия в системе.

Отличие от [`zoom:backfill-attendance`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Console/Commands/BackfillZoomAttendance.php)
(H3085), которая остаётся для своего случая: та **создаёт** занятия и делает
`updateOrCreate` — в боевых данных волны 3 и то и другое запрещено.

## Три развилки — решены человеком 31-08-2026

Диагноз оставлял человеку три вопроса; все три закрыты в тот же день.

### 1. Идентификация участников — «чини, и пропиши в руководствах»

Починка сделана в двух половинах, потому что у задачи две половины.

**Назад.** [`attendance:link-participants`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Console/Commands/LinkWebinarParticipants.php)
заводит связки «экранное имя в Zoom → пользователь» в отдельной таблице
`webinar_participant_links`. Отдельной, а не в `webinar_attendances`: волне 3 запрещены
UPDATE, и человек должен иметь возможность пересмотреть связку, не трогая исходные данные
Zoom. Плашка покрытия теперь считает и через связки — иначе она продолжала бы показывать
ноль при сотнях собранных строк.

Сопоставление ([`ZoomNameMatcher`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Support/ZoomNameMatcher.php))
сравнивает **наборы токенов**, а не строки целиком: точное равенство `users.name` даёт
0 совпадений из 1218. Латиница приводится к кириллице («Anna Ivanova» = «Анна Иванова»),
порядок слов не важен, подписи устройств («iPhone», «Galaxy») отсеиваются до транслита —
иначе «iphone» превращается в «ипхоне» и участвует в сопоставлении как обычное слово.
Кандидаты всегда ограничены плательщиками одного курса: на множестве в десятки человек
совпадение по одному слову ещё осмысленно, на всей базе было бы шумом. Уверенность не
схлопывается: `strong` — совпали имя и фамилия, `weak` — одно слово (заводится только
с `--weak`), неоднозначное **не угадывается** и уходит человеку.

Замер на боевых данных курса 375: 28 плательщиков, 30 различных подписей в Zoom —
**11 подписей сопоставлены, 10 плательщиков из 28 узнаны**, 3 неоднозначны, 16 не
опознаются в принципе (устройства и номера телефонов). Было 0.

**Вперёд.** Причина в том, как студент подписан в Zoom, поэтому это записано в
руководства, а не только в код:

- [руководство ученика](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/STUDENT_CABINET_GUIDE_RU.md)
  — шаг «входите под своим именем и фамилией» прямо в сценарии «Открыть следующий урок»,
  плюс ответ «ходил, а посещаемость пустая»;
- [руководство куратора](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/CURATOR_ADMIN_GUIDE_RU.md)
  — сценарий «Ученик ходил, а посещаемость пустая»: сначала переименование, потом ручная
  связка за прошедшее, и честное «за прошлый поток может быть невосстановимо»;
- [памятка бухгалтера](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/MANUAL_ACCOUNTANT_COURSE_STREAMS_RU.md)
  — что именно означает плашка покрытия и почему до 25-03-2026 её нет вовсе.

### 2. Заведение занятий первого потока — «заводи, человек сейчас ничего не видит»

Решение принято: без занятий курс 332 показывает пустоту, и цифры для человека мертвы.
[`attendance:backfill-streams --create-lessons`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Console/Commands/BackfillStreamAttendance.php)
заводит занятие под подтверждённый запуск Zoom — по-прежнему **только вставками**.

Заведение обязательно требует `--slot` («Wed,12:30-15:30»): без окна занятия команда
приняла бы за урок любой запуск общей комнаты, а в ней проходили и другие активности —
воскресный вечер 15-02-2026 на 57 человек к курсу 332 отношения не имеет. Вместе с
`--min-participants` окно отсекает и служебные запуски. Заголовок заведённой строки
помечен «бэкфил H3761», чтобы её было видно среди расписания, которое человек вёл сам.

### 3. Занятие 24-06-2026 — «не было»

Подтверждено человеком: занятия в этот день не проводилось. В Zoom запуска на эту дату
нет, и это совпадает. Строка 643 остаётся в расписании как след, но посещаемости у неё
не будет никогда — это не пропуск сбора.

## Что реально произошло на проде 31-08-2026

Развёрнуто `39b3535c`, смоук `samskrte.ru` → 200. Все прогоны — сначала сухие, потом
`--apply`, как требует контракт волны.

### Курс 375 — досбирать оказалось нечего, и это правильный результат

Сухой прогон подтвердил диагноз до последней строки: 13 занятий с источником в Zoom,
**к вставке 0 строк** — вебхук и живая сверка уже собрали всё. Единственное слепое
занятие — **24-06-2026**, ровно то, про которое человек сказал «не было». Пять запусков
Zoom 03-03…03-18 остались без занятия: это хвост первого потока в той же комнате.

### Курс 332 — первый поток поднят из Zoom

```
attendance:backfill-streams --course=332 --meeting-id=… \
  --since=2025-09-01 --until=2026-03-24 --slot=Wed,12:30-15:30 \
  --min-participants=5 --create-lessons --apply

Итого к вставке: 529 строк.
Заведено занятий: 20. Вставлено строк посещаемости: 529.
```

20 сред с 17-09-2025 по 18-03-2026, в каждой 18–48 участников. Окно `Wed,12:30-15:30`
отсекло всё, что комнатой пользовалось помимо курса, — воскресный вечер 15-02-2026 на
57 человек и служебные запуски на одного. Слепых занятий у 332 не осталось: ни одной
даты, где занятие есть, а источника нет.

**Повторный прогон той же командой: «Итого к вставке: 0 строк. Заведено занятий: 0».**
Идемпотентность проверена на боевых данных, а не только в тесте.

### Плашка покрытия — цифры ожили

Замерено через сам сервис [`CourseStreamComparisonReport`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Services/CourseStreamComparisonReport.php),
то есть ровно то, что видит человек на экране «Потоки курса»:

| Показатель | Было | Стало |
|---|---|---|
| покрыто плательщиков | 17 из 70 | **30 из 70** |
| покрытие | 23,9 % | **42,9 %** |
| узнано по вебинарам (`webinar_users`) | **0** | **19** |
| из просмотров записей | 17 | 17 |

Связок «имя в Zoom → пользователь» заведено 45 (33 по всем курсам + 12 по 332 после
бэкфила). Ни одна строка `webinar_attendances` при этом не изменена.

### Четверги первого потока — заведены (H3771, решение человека в тот же день)

На вопрос «четверги тоже?» человек ответил «да, четверги тоже заводи», и они добраны
тем же прогоном:

```
attendance:backfill-streams --course=332 --meeting-id=… \
  --since=2025-09-01 --until=2026-03-24 --slot=Thu,12:00-15:30 \
  --min-participants=5 --create-lessons --apply

Заведено занятий: 2. Вставлено строк посещаемости: 34.
```

**Окно пришлось расширить до 12:00, а не 12:30.** Занятие 01-01-2026 началось в
**12:29** по местному времени — на одну минуту раньше среды́шного окна, и `Thu,12:30-…`
потеряло бы его молча. Это общее свойство слотов: граница окна — не расписание, а
наблюдение, и её надо сверять с фактическим временем запусков.

Четыре запуска 01-01-2026 (класс в 12:29 на 19 человек плюс три переподключения ведущего
по одному участнику) сгруппировались в **одно** занятие на 22 сессии участия — так и
задумано: группировка идёт по календарной дате, а не по запуску. Повторный прогон:
`Заведено занятий: 0. Вставлено строк посещаемости: 0`.

Итог по курсу 332: **22 занятия** (20 сред + 2 четверга) и **563 строки посещаемости**.
`webinar_users` по семье поднялся с 19 до **20**; общее покрытие осталось 30 из 70
(42,9 %) — новый узнанный человек уже числился покрытым по просмотрам записей.

### Решено: 22 занятия и 16 уроков — это две разные вещи, и так и остаётся

**Решение человека 31-08-2026: оставить как есть.** Нумерация «1/16»…«16/16» в карточке
курса 332 — это **оглавление контента**, а не счётчик встреч, и переименовывать её под
22 проведённых занятия не нужно.

Почему это правильный ответ, а не отложенный. Уроки и занятия отвечают на разные вопросы:
урок — единица материала, которую студент открывает в кабинете; занятие — факт живой
встречи в Zoom, к которому цепляется посещаемость. Одна встреча может не дать нового
урока (разбор, ответы на вопросы, перенос), а один урок может разойтись на две встречи.
Приведение одного к другому не уточнило бы ни то ни другое, зато сломало бы ссылки на
уроки и разошлось бы с записями курса 424 («в записи»), где нумерация та же.

**Практическое следствие для чтения экрана:** расхождение 22 против 16 — не дефект и не
