## Шаг 0. Изоляция и подготовка

Работа идет в отдельном worktree, не в главном дереве — репозиторий под защитой хука.

```
git -C <путь к Systema-Sanscriticum> fetch origin
git -C <путь к Systema-Sanscriticum> worktree add -b h2501-teacher-guide \
    ../Systema-Sanscriticum-h2501-<pid> origin/main
```

Зависимость: нет. Дальше все шаги — внутри этого worktree.

Волне 1 `vendor/` нужен только на шагах 4–7 (artisan, тесты, сборка PDF). Если каталог в
worktree отсутствует — копировать роботом (`robocopy`), не создавать junction: junction на
`vendor/` в этом проекте уже приводил к порче основного дерева.

## Шаг 1. Перепись навигации — раньше текста, а не после

Порядок неочевиден и потому объясняю: перепись идет **первой**, потому что она дает
оглавление. Писать текст, а потом узнавать, что забыли три раздела, — это переписывание.

Файл: `app/Console/Commands/TeacherNavCensus.php`

1. Команда `teacher:nav-census`.
2. Берет пользователя-преподавателя из фикстуры (создает в памяти либо использует фабрику; прод не трогаем).
3. Проходит `Filament::getResources()`, `getPages()`, `getWidgets()` панели администратора.
4. Для каждого спрашивает `canViewAny()` / `canAccess()` и `shouldRegisterNavigation()` от имени этого пользователя.
5. Пишет `docs/generated/teacher_nav_census.json`: `group`, `label`, `class`, `url`, `kind`.
6. Печатает сводку: сколько видно всего, сколько по группам.

Зависимость: шаг 0. На выходе — фактический список того, что видит преподаватель.

Ожидаемая частность: в списке окажутся разделы из «Маркетинга», «Продаж» и «Финансов». Это не
ошибка команды, а та самая находка. Не исправлять код — зафиксировать (шаг 9).

## Шаг 2. Скелет гида из результата переписи

Файл: `docs/TEACHER_CABINET_GUIDE_RU.md` (новый)

1. Шапка с датами, оглавление, четыре части по
   [архитектуре §3](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/ARCHITECTURE_SYSTEMA_TEACHER_CABINET_GUIDE.md).
2. Легенда бейджей обратимости — сразу после оглавления, до первого сценария.
3. В части II — по одному заголовку `###` на каждый раздел из переписи, пока пустому.
4. Разделы, которые преподаватель видит, но которые ему не нужны, получают одну строку: что это и почему его не касается. Не удалять из оглавления: преподаватель их видит, значит про них спросит.

Зависимость: шаг 1 (без JSON нечего раскладывать).

## Шаг 3. Наполнение текстом

Тот же файл. Порядок внутри шага — от самого частого к редкому, чтобы при нехватке времени
недописанным осталось наименее нужное.

1. **Часть I, семь сценариев.** Скелет каждого: зачем → шаги с бейджами → что увидит студент → если пошло не так.
2. **Перенос текста из HTML.** Все 12 глав старого гида переезжают в часть II в сокращенном виде: что это, где лежит, что можно менять. Пошаговые инструкции из них уходят в часть I, а не дублируются.
3. **Влить SRS.** Раздел «Добавить карточки в колоду» собирается из [MANUAL_TEACHER_SRS_KOLODA_RU.md](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/MANUAL_TEACHER_SRS_KOLODA_RU.md). Сохранить его ключевое утверждение: источник правды — Systema, а не Memrise.
4. **Часть III.** «Что нельзя сломать»: список необратимых действий с адресом, куда идти за откатом. Сюда же — глава про запреты из старого гида и ссылка на [TEACHER_SITE_DOWN_CHEATSHEET_RU.md](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/TEACHER_SITE_DOWN_CHEATSHEET_RU.md).
5. **Часть IV.** Пять вопросов старого FAQ плюс новые из сценариев; два чек-листа сохранить.
6. **Денежные экраны — только чтение** (R7): где смотреть нагрузку, начисления, взаиморасчеты. Ни одной инструкции по операциям.

Правила текста — §4 [MANUALS_TO_UI_CONTENT_AUDIT_2026.md](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/MANUALS_TO_UI_CONTENT_AUDIT_2026.md):
русский, никаких внутренних имен классов и ролевых гейтов, говорим результат, а не механику.
Названия разделов — дословно как в интерфейсе, иначе преподаватель не найдет их глазами.

Зависимость: шаг 2.

## Шаг 4. Переключение сборки PDF на Markdown

Файл: [docs/build-teacher-guide.php](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/build-teacher-guide.php)

1. Вместо `file_get_contents` HTML — чтение `.md` и разбор через CommonMark.
2. Обернуть в минимальный HTML-каркас со стилями для печати: шрифт DejaVu Sans, таблицы, цитаты.
3. Колонтитул и параметры страницы оставить как есть — они работают.
4. Прогнать сборку, открыть PDF, проверить глазами: таблицы не разъезжаются, цитаты видны, бейджи обратимости на месте и не превратились в прямоугольники.
5. Удалить `docs/teacher-guide.html`.

Зависимость: шаг 3. Удаление HTML — последним действием шага, не раньше: пока PDF не собрался из нового источника, старый файл остается страховкой.

## Шаг 5. Страница гида в панели

Файлы: `app/Filament/Pages/TeacherGuide.php`, `resources/views/filament/pages/teacher-guide.blade.php`

1. Страница: заголовок «Руководство преподавателя», группа навигации «Обучение», иконка из имеющегося набора.
2. `canAccess()` — админ, редактор лекций или пользователь с `teacher_id`; опираться на `User::isTeacher()` ([app/Models/User.php](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Models/User.php), строка 309), не изобретать вторую проверку.
3. Шаблон читает `base_path('docs/TEACHER_CABINET_GUIDE_RU.md')` и рендерит через `Str::markdown()`.
4. Путь — константа в коде. Параметра «какой файл показать» нет и быть не должно: неэкранированный вывод безопасен ровно потому, что источник закоммичен в репозиторий и никогда не приходит из запроса.
5. Файла нет — одна строка «руководство не найдено», без исключения.
6. Стили: не изобретать свою типографику, взять `prose`-классы, уже используемые в проекте.

Зависимость: шаг 3 (файл должен существовать).

## Шаг 6. Тест покрытия

Файл: `tests/Feature/TeacherGuideCoverageTest.php`

1. Запускает перепись, читает JSON.
2. Утверждает: у каждого элемента переписи есть заголовок в `docs/TEACHER_CABINET_GUIDE_RU.md` (сверка по названию раздела, нормализованно).
3. Утверждает: страница гида доступна пользователю с `teacher_id` и отдает 200; постороннему — 403.
4. Утверждает: файл гида существует и не пуст.

Зависимость: шаги 1, 3, 5. Этот тест — механическая половина приемки; вторая половина, живой прогон преподавателем, идет уже после выпуска.

## Шаг 7. Проверка свежести в CI

Файл: рабочий процесс в `.github/workflows/` (шаг в существующем, если подходит — не заводить новый файл ради одной проверки)

1. На pull request сравнить измененные пути с наблюдаемым списком из [архитектуры §6](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/ARCHITECTURE_SYSTEMA_TEACHER_CABINET_GUIDE.md).
2. Если пересечение есть, а `docs/TEACHER_CABINET_GUIDE_RU.md` не менялся — напечатать предупреждение с перечнем задевших файлов.
3. Шаг завершается успешно всегда. Предупреждение, не блок: изменение бывает чисто внутренним, и блок заставлял бы дописывать в гид пустую строку ради зеленого CI.

Зависимость: шаг 3.

## Шаг 9. Находка по навигации — в GitHub-issue

Отдельный от кода результат волны 1 (R1).

1. Проверить открытые issue на дубликат.
2. Открыть issue: что видит преподаватель по факту (данные шага 1), почему это дорого (жалоба преподавателя дословно), сколько ресурсов имеют гейт с упоминанием преподавателя (9 из 190), какие группы навигации лишние.
3. Приложить `docs/generated/teacher_nav_census.json` как доказательную часть.
4. Кода не касаться. Правку гейтов решает человек — это волна 3 и отдельный handoff.

Зависимость: шаг 1.

## Шаг 10. Сдача

1. Коммит по правилу безопасной фиксации для этого репозитория (в проекте есть наблюдатель за файлами — обычный `git add -A` из главного дерева тут неуместен).
2. Push ветки, pull request, слияние, затем выкладка на прод по известному пути этого проекта — страница в панели без выкладки читателю не видна.
3. Один дымовой прогон после выкладки: открыть страницу гида в `/admin` аккаунтом преподавателя, убедиться, что текст отображается. Отчет — PASS или FAIL, не «проверьте, пожалуйста».
4. Убрать worktree сразу после подтвержденного слияния.

Зависимость: шаги 1–9.
