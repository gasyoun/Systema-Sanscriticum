## 1. Goal

Multiply curator throughput on the Telegram support lane (Support-account DMs + the @rusamskrtam second session) so that **≥60 % of inbound support DMs close with zero curator typing** by 31-10-2026 (auto-send or one-tap draft), with a **first response ≤15 min in working hours** and **precision ≥95 % on every auto-sent category**. The 31-08 plan built the shadow-mode lane, the BM25 FAQ retriever and the category-F live path; FINDINGS §635 then showed that only ~2 % of DM traffic is FAQ-shaped — most tickets are about one student's own facts (next class, link, recording, homework, balance, access). This plan therefore leads with **deterministic LMS-fact resolution** and **one-tap delivery**, adds an **SLA timer**, and folds the GPU-node stages 3–5 of #1633 (hybrid retrieval, indexer, shadow local generation) in as Opus 5 handoffs, replacing the idle Grok handoff H3234. Every student-visible expansion passes the same shadow → curator-reviewed precision → human flag flip gate that category F passed.

Baseline on 02-09-2026: H3765 + H3766 executed 31-08 (shadow lane live, `SUPPORT_DM_AUTO_REPLY_SHADOW` ON on prod, 80Q eval set recall@5 83 %, MRR 0.713); H3799 live FAQ auto-send category F only (PR #2242, shadow-week verdict not before 07-09); GPU node live since 01-09 19:00 UTC (`qwen3:14b` + `bge-m3` behind the sshd reverse tunnel to `.92`); ~226 inbound DMs per 30 days.

## 4. Autonomy contract (verbatim for every execution agent)

1. **On ambiguity:** pick the marked default, log it in the handoff's decisions log (the PR body), and continue. Unlisted forks resolve toward «no student-visible change, flag default OFF, shadow first»; the log row names the alternative not taken. Never block waiting for a human mid-wave.
2. **Stop conditions (halt the wave, report):** (1) anything that would send to a student outside the shadow / live-category list, including categories D (payment) and E (access); (2) any WRITE to money-contour code or tables; (3) destructive DB operations; (4) the test suite red after two fix attempts; (5) prod deploy failing its smoke; (6) the tunnel to `.92` down at build time for stage-3/5 work (finish the tunnel-independent steps, then halt); (7) a MadelineProto session error on either account; (8) PII appearing in any file about to be committed.
3. **Commit authority:** worktree off `origin/main` → PR → merge without re-asking (handoff-scoped autonomy) → deploy after merge only via deploy.sh per docs/deploy.md — never a hand `git pull` on prod. Every new env flag defaults OFF; money-contour PRs carry the marker + money tests and still merge. Live flag flips (V1) and the stage-6 local-generation flip stay human and are recorded in GTD.
4. **The fence (never touch):** the MadelineProto support sessions (both accounts) and their auth files; `TelegramSendGuard` claims are mandatory before ANY new Telegram send point (incident 24-08-2026); no LLM model installs on `.92` and no student traffic through the n8n `.91` node (#1633 bans); no tunnel or sshd config changes on `.92`/`.91`; no OpenRouter model swap; never feed `docs/**` to students; prices only from the course catalog; no writes to `Payment`/`Group`/`Tariff` from any support code; no schema change to `telegram_support_messages` beyond additive nullable columns; the ORS-FAQ `ors_faq/dialogs/` PII store is out of scope entirely; no edits to tracked files on the prod VPS; the external watcher reverts uncommitted main-tree changes — use /watcher-safe-commit.
5. **Shadow-mode invariant:** while a category, resolver or the clarifying question is in shadow, the student-visible behaviour of the lane must be byte-identical to today's. Any diff in outbound traffic during shadow = defect, halt.
