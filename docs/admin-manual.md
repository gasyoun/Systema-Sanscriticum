# Руководство администратора — функции последнего месяца (06.06–06.07.2026)

_Created: 06-07-2026 · Last updated: 30-07-2026_

> **Клипы лекций / n8n:** операторское руководство — [MANUAL_N8N_LECTURE_CLIPS_OPERATOR_RU.md](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/MANUAL_N8N_LECTURE_CLIPS_OPERATOR_RU.md); установка n8n — [issue #666](https://github.com/gasyoun/Systema-Sanscriticum/issues/666).

Документ описывает **новые/измененные admin-панельные функции**, слитые в `main` за
последний месяц (с 06.06.2026 по 06.07.2026), для роли **администратор/супер-админ**
и, где отмечено, **куратор** (роль `manager`) и **преподаватель** (роль `teacher`).
Это не полное руководство по всей панели — только дельта последнего месяца.
Чисто витринные/лендинговые/SEO-функции (без экрана в `/admin`) сюда не включены —
они не являются «функцией, которой пользуется админ».

> **Финансовый функционал** (Финансовый штурвал, Планирование, Зарплаты, Выплаты,
> Расходы, скидки/промо в деньгах) вынесен в отдельный документ —
> [`finance-manual.md`](finance-manual.md), рассчитанный на бухгалтера. Здесь эти
> разделы не дублируются, только упоминаются со ссылкой.

> **Раздел «Должники»** уже подробно описан в отдельном
> [`debtors-manual.md`](debtors-manual.md) — здесь описана только дельта последнего
> месяца (год-фильтр, авто-напоминания) и новый read-only отчет «Реактивация».

> **Как это видит сам студент** (личный кабинет, а не `/admin`) — отдельный документ
> [`student-manual.md`](student-manual.md) (H229). Полезно при разборе тикетов
> куратором: там же описаны самодиагностика доступа и вкладка «Прана».

**Обозначение ролей в каждом разделе** — кто видит пункт меню и может им пользоваться
(проверено по коду `canAccess()`/`canViewAny()`/`RoleGate::*`, не по названию фичи):

| Обозначение | Кто видит |
|---|---|
| 🔴 Только админ | `RoleGate::adminOnly()` — админ + супер-админ |
| 🟡 Админ или куратор/менеджер | `RoleGate::any(ADMIN, MANAGER)` |
| 🟢 Админ или преподаватель | `RoleGate::any(ADMIN, TEACHER)` |
| ⚪ Любой с доступом в панель | нет явного гейта — виден admin/teacher/manager/accountant (кроме супер-админа — тот видит всё всегда) |
| 🔵 Не преподаватель | `!isTeacher()` — видят все роли, кроме преподавателя |

## 1. CRM / куратор / поддержка

### 1.1. Диалоги с ИИ и студентами (Helpdesk) — вкладки и ergonomics (#324, H223)

**Где:** `/admin/dialogs` — пункт меню «Чат с куратором».
**Доступ:** 🔵 не преподаватель (`canAccess()`: `!isTeacher()`) — видят админ, супер-админ,
куратор (`manager`), бухгалтер.

Единая страница диалогов поддержки (Telegram/VK/веб-чат кабинета), сведенных в одну
ленту через `SupportConversationManager` + `UnifiedInboxReader`.

**Что нового за месяц:**
- **Вкладки списка диалогов**: `inbox` (общая очередь) / `mine` (назначенные на меня) /
  `resolved` (закрытые) — переключаются над списком, сокращают число кликов при
  разборе очереди.
- **Модалка карточки студента** прямо из диалога — клик по имени открывает инфо
  (курсы, прогресс, статус должника) не выходя из чата.
- **Бэйдж куратора** у студента + трекинг «кто и когда последним отвечал» — виден в
  списке диалогов и на карточке.
- **Очередь одобрения напоминаний** — куратор видит предложенные системой напоминания
  (см. §1.3) и подтверждает/отклоняет их прямо из чата.
- **ИИ-резюме диалога** — краткая выжимка треда (за флагом `support_ai_assist`).

**Готчас:** вкладка `mine` фильтрует по назначенному куратору — если диалог никому не
назначен, он останется только во вкладке `inbox`.

### 1.2. Поддержка: команда ранжирования тем (#301)

**Где:** консольная команда `support:topic-ranking` (не UI-экран сама по себе), но
результат правит справочники в разделе **Пользователи → Telegram support**:
- **Темы** (`/admin/telegram-support/support-topic-rules`) — 🔵 не преподаватель.
- **Ответчики** (`/admin/telegram-support/support-responder-mappings`) — 🔵 не преподаватель.
- **Контакты** (`/admin/telegram-support/telegram-support-contacts`) — 🔵 не преподаватель.

Все три собраны в кластер **TelegramSupport** (гейт кластера — тот же `!isTeacher()`,
чтобы пустой пункт меню не светился преподавателям).

Команда пересчитывает приоритет тем поддержки для self-serve сортировки очереди;
результат отражается в весах, которые видно в разделе «Темы».

### 1.3. Обнаружение запроса напоминания в чате + очередь одобрения куратором

**Где:** **Пользователи → Предложения напоминаний** (`ReminderSuggestionResource`) +
встроено во вкладку диалогов Helpdesk (§1.1).
**Доступ:** ⚪ явного гейта на ресурсе нет — виден всем ролям с доступом в панель.

Когда студент в чате пишет что-то похожее на просьбу «напомни мне о …», система
создает черновик `ReminderSuggestion`. Куратор видит предложение в очереди и решает:
одобрить (создаст `ScheduledReminder`, см. §1.4) или отклонить.

### 1.4. Персональные напоминания по расписанию (ScheduledReminder)

Модель напоминаний, создаваемых из одобренных предложений (§1.3) или вручную —
разовое напоминание конкретному студенту на конкретную дату/время, доставляется через
подключенный канал (TG/VK).

**Готча:** это отдельный механизм от массовых авто-напоминаний должникам/по занятиям
(они настраиваются в **Глобальные настройки**, см. §2.4) — `ScheduledReminder`
одноразовый и привязан к конкретному студенту.

### 1.5. Инструменты маркетолога для лидов — воронка, письмо/DM, история общения

**Где:** `/admin/leads` (`LeadResource`).
**Доступ:** 🟡 админ или менеджер (`RoleGate::any(ADMIN, MANAGER)`).

К карточке лида добавлены:
- **Воронка** — визуальный статус лида по стадиям.
- **Письмо/DM** — отправка сообщения лиду прямо из карточки (email или мессенджер).
- **История общения** — журнал всех контактов с лидом (заметки — `NotesRelationManager`
  на связанном ресурсе).

### 1.6. FAQ-суггестер ответов — готовые черновики для куратора (H247/H816/H1838)

**Где:** встроено в диалоги Helpdesk (§1.1) — под входящим фактологическим вопросом
студента появляется черновик ответа с кнопками **Принять / Изменить / Отклонить**.
Отдельного экрана нет; бот сам НИЧЕГО не отправляет — решение всегда за куратором.
**Доступ:** тот же, что у Helpdesk (§1.1).

Каждые 15 минут система сканирует новые входящие (веб-чат + импортированный
TG-support) и, опознав вопрос одной из шести категорий, готовит черновик. Откуда
берётся текст — три источника, по категориям:

- **A/B/C — Zoom-ссылка / записи / расписание:** черновик собирается из живых данных
  LMS (расписание, уроки) без ИИ (H247).
- **D/E/F — оплата-тарифы / доступ-группа-кабинет / материалы-ДЗ-сертификаты, с
  привязанным шаблоном:** черновик строится из шаблона библиотеки **Маркетинг →
  Шаблоны сообщений** (поле «Категория FAQ-суггестера») с подстановкой
  `{name}`/`{pay_link}` — мгновенно, без расходов на ИИ и всегда одним выверенным
  текстом (H1838).
- **D/E/F без шаблона:** черновик формулирует внешний ИИ по фактам LMS (цены — только
  из кода тарифов, ничего не выдумывается), за флагом `support_ai_assist` и дневным
  лимитом вызовов (H816).

**Как поменять текст готовых ответов:** правьте привязанный шаблон в «Шаблонах
сообщений» — со следующего скана черновики пойдут с новым текстом. Привязка — одна
категория → свежайший активный шаблон с этой пометкой.

**Тумблеры:** админ-тумблер FAQ-суггестера в **Маркетинг → Глобальные настройки**
(`support_answer_suggester_enabled`) + деплой-флаги в `.env`:
`SUPPORT_ANSWER_SUGGESTER`, `SUPPORT_TEMPLATE_DRAFTS`, `SUPPORT_AI_ASSIST`.
Состояние прода с 30-07-2026: суггестер и шаблонные черновики ВКЛ, шаблоны D/E/F
привязаны (#1–#3), ИИ-путь ВЫКЛ — ноль расходов на LLM.

**Готчас:** черновик без фактов не создаётся вовсе — пустых подсказок куратор не
видит; pending-черновики старше 14 дней истекают автоматически.

## 2. Студенты, должники, реактивация

### 2.1. Мульти-канальное еженедельное напоминание никогда-не-логинившимся (#316)

**Где:** настройка канала — **Маркетинг → Глобальные настройки**
(`MarketingSettingResource`, доступ ⚪ любой с панелью); срабатывает автоматически по
расписанию (cron).

Студентам, которые ни разу не заходили в кабинет, раз в неделю уходит напоминание —
пробует все привязанные каналы (Telegram/VK/email) по очереди, а не только один.

### 2.2. Дисциплина оплаты студента и группы (#305)

**Где:** карточка студента → раздел «Дисциплина» (`UserResource`, вкладка
`ViewEntry::make('discipline_score')`); агрегат по группе — виджет
`DisciplineByGroupWidget` на дашборде куратора/админа.
**Доступ:** карточка студента — как обычно у `UserResource` (админ-подобные + куратор);
виджет `DisciplineByGroupWidget` — см. код виджета для точного гейта по роли.

Числовой скор «насколько студент платит вовремя» — считается по истории платежей
относительно сроков блоков. Показывается и на уровне студента, и агрегированно на
уровне группы (средний скор группы — сигнал куратору, где нужно усилить внимание).

**Готча:** это не то же самое, что «Должники» — скор смотрит на историю
своевременности, должники — на текущий факт неоплаты предстоящего блока.

### 2.3. Мягкий выход студента из группы без потери доступа

**Где:** карточка студенческой группы → действие над участником
(`StudentGroupResource`, `StudentsRelationManager`).
**Доступ:** 🟢 админ или преподаватель (`RoleGate::any(ADMIN, TEACHER)`).

Позволяет вывести студента из активного списка группы (например, при переходе в
другой поток), не отзывая уже открытый доступ к урокам — раньше единственный вариант
был полное удаление из группы, которое рвало доступ.

### 2.4. Должники — дельта месяца (полное руководство: [`debtors-manual.md`](debtors-manual.md))

**Где:** `/admin/debtors`. **Доступ:** 🔴 только админ (`RoleGate::adminOnly()`).

За последний месяц в существующий раздел «Должники» добавлено:
- **Год-фильтр** должников по дате блока — не смешивает старые и текущие потоки одного
  курса; выбор запоминается глобально (в `MarketingSetting`) и восстанавливается при
  возврате на страницу.
- **Напоминание о скором неоплаченном следующем блоке** — проактивное уведомление до
  наступления просрочки, не только когда блок уже не оплачен.
- **Авто-напоминания должникам** по TG/VK/email — тумблеры включения и **редактируемое
  время отправки** (было — фиксированное время в коде).
- **Email-канал** в напоминаниях (раньше — только TG/VK) + прямая ссылка на курс в письме.
- **Трекинг привязки бота**: дата привязки, счетчик-виджет «сколько студентов привязали
  бота», экспорт списка.
- Правило «блоки до присоединения студента к потоку не считаются долгом» —
  фикс логики расчета, чтобы не помечать должником того, кто присоединился позже.

Все настройки тумблеров/времени — в **Маркетинг → Глобальные настройки**.

### 2.5. Реактивация — read-only отчет (#203, новый раздел)

**Где:** `/admin/reactivation` — пункт меню «Реактивация».
**Доступ:** 🔴 только админ (`canAccess()`/`shouldRegisterNavigation()`:
`RoleGate::adminOnly()`).

Отдельная страница поверх той же модели данных, что и «Должники»
(`DebtorsReport`), но **read-only** — витрина для приоритизации, кого из
неактивных/просроченных студентов стоит попробовать вернуть, без случайных правок
прямо на боевом отчете должников. Колонки и фильтры — подмножество «Должников»,
акцент на давности последней активности.

**Готча:** это не отдельный источник данных — изменения в самой модели долга
(например, подтверждение оплаты) делаются через «Должники», не здесь.

### 2.6. Карточка прогресса студента для кураторов (#160)

**Где:** карточка студента (`UserResource` → `ViewUser`), вкладка прогресса.
**Доступ:** как у карточки студента в целом.

Показывает куратору сводный прогресс студента по курсу: пройдено уроков, статус ДЗ,
последняя активность — не заходя в детальный лог каждого урока.

### 2.7. Очередь проверки ДЗ для кураторов (#159) + видимость статуса (#162)

**Где:** `/admin` → «Домашние работы» / «Проверка ДЗ» (`HomeworkSubmissionResource`).

**Стереть ошибочно залитое (H2120 + #1028/#1030).** Студент сам: корзина у
своего файла и сообщения в кабинете, пока статус не «Принято» (в т.ч. «На
проверке»). Штат на карточке работы: корзина у **любого** файла в треде; в
шапке — **«Стереть файлы студента»** (все студенческие вложения с диска +
статус «На доработку»).
**Доступ:** 🟢 админ или преподаватель (`RoleGate::any(ADMIN, TEACHER)`).

- **Очередь проверки**: bulk-действия (пометить пачкой), фильтры (по курсу/группе/
  статусу), шаблоны быстрых комментариев при проверке.
- **Видимость статуса ДЗ** для студента в кабинете: «не задано» / «скоро дедлайн» +
  мгновенный пуш при новом ДЗ — это студенческая сторона, но настраивается через тот
  же ресурс (шаблон уведомления).

### 2.8. Реальные аватарки студентов из Telegram/VK + таблица «Студенты» (#…)

**Где:** таблица `/admin/users` (`UserResource`), колонка аватара.
**Доступ:** обычный доступ к `UserResource`.

Вместо заглушки-инициалов подтягивается реальное фото профиля из привязанного
Telegram/VK, если он подключен; иначе — прежний фолбэк.

### 2.9. Telegram @username студента — захват, показ, бэкфилл

**Где:** карточка студента (`UserResource`), поле username рядом с привязкой TG.
**Доступ:** обычный доступ к `UserResource`.

При новой привязке username захватывается автоматически; для уже привязанных ранее
студентов — разовый бэкфилл (одноразовая команда/джоба, не постоянный экран).

**Готча:** username в Telegram может отсутствовать (не у всех аккаунтов он задан) —
поле в этом случае остается пустым, это не ошибка синхронизации.

### 2.10. Онбординг: нормализация email, самопроверка входа, рассылка спящим (#218)

**Где:** онбординг-флоу кабинета студента (не отдельный админ-экран), плюс сегмент
«спящие» в рассылке (**Пользователи** → массовая рассылка, см. §1 общей рассылки).
**Готча для админа:** нормализация email на этапе регистрации означает, что поиск
студента по email в `UserResource` может не совпасть по регистру/пробелам со старыми
записями, заведенными до нормализации, — использовать поиск по частичному совпадению.

### 2.11. Тариф «пол блока» при ручном создании платежа

**Где:** **Финансы** → «Создать» → поле «Тариф» → `Блок N — 1-я/2-я половина`.
Это финансовая функция — подробно описана в [`finance-manual.md`](finance-manual.md) §Тарифы;
здесь упомянута, т.к. затрагивает и доступ к урокам (открывает только уроки своей
половины блока), что видно и в карточке студента.

### 2.12. Короткая ссылка `/u/{id}` на карточку студента

**Где:** доступна с карточки студента как «поделиться» / копируется вручную из URL.
**Доступ:** та же роль, что и обычный доступ к карточке — сама короткая ссылка не
меняет права, только удобство (для заметок в Telegram при переписке о конкретном
студенте не тащить длинный URL Filament-ресурса).

### 2.13. Короткие URL курсов и уроков

**Кабинет:** `/c/{slug}` (курс), `/c/{slug}/u/{lessonId}` (урок).  
**Витрина:** `/k/{slug}`, preview — `/k/{slug}/preview`.

Старые path (`/course/.../lesson/...`, `/online/kursy/...`) отвечают **301** на
короткие. `slug` курса — короткий канон (пример: `hindi-2_sb1300-2026`); при
смене slug в карточке курса прежний пишется в `course_slug_aliases` и тоже
редиректит 301. Массовое переименование: `php artisan courses:shorten-slugs map.tsv --dry-run` / `--apply`.

Не путать с `/u/{id}` карточки студента (п. 2.12) — там top-level `/u/`, здесь
вложенный `/c/.../u/...` = урок.

## 3. Посещаемость, вебинары, уроки

### 3.1. Zoom-интеграция Phase 1–3 (#194, #195, #197)

**Где:** настройка привязки — карточка курса/расписания (`CourseResource`,
`ScheduleResource`); данные посещаемости — **Аналитика студентов**
(`TeacherAnalytics`, §3.2).
**Доступ к расписанию:** 🟢 админ или преподаватель.

Три фазы одной интеграции:
1. **Phase 1 — автосоздание встречи** из записи в расписании (не нужно вручную
   создавать Zoom-встречу и копировать ссылку).
2. **Phase 2 — автоимпорт записи** через вебхук `recording.completed`: как только Zoom
   заканчивает обработку записи, ссылка на нее подтягивается в занятие автоматически.
3. **Phase 3 — посещаемость через participant-вебхуки**: кто и сколько времени провел
   на встрече, без ручной сверки списков.

**Готча:** посещаемость строится на вебхуках Zoom — если вебхук не долетел (сетевой
сбой на стороне Zoom), запись о присутствии может не появиться; ручной импорт как
резервный путь не описан отдельно — если данные разошлись, проверить журнал вебхуков.

### 3.2. Посещаемость вебинаров в «Аналитике студентов» (#198)

**Где:** `/admin/teacher-analytics`.
**Доступ:** 🟢 преподаватель видит свою аналитику, админ-подобные — по всем курсам
(`canAccess()`: `isTeacher() || isAdminLike()`).

Дашборд аналитики пополнился блоком посещаемости Zoom-занятий — рядом с прежними
метриками прогресса/активности.

### 3.3. Учет посещаемости Zoom-занятий под единую ссылку курса

Для курсов, где на все занятия используется **одна и та же** Zoom-ссылка (не новая
встреча на каждое занятие), посещаемость теперь считается корректно по времени
занятия, а не смешивается в одну запись на весь курс.

### 3.4. Порядок уроков внутри группы + бейдж группы в админке

**Где:** `LessonResource` — поле сортировки уроков, зависящее от группы; бейдж группы
в списке уроков.
**Доступ:** обычный доступ к `LessonResource`.

Позволяет задать разный порядок прохождения уроков для разных групп одного курса
(если поток идет не строго по номерам уроков).

### 3.5. Редактор лекций — Phase A/B/C

**Где:** отдельная панель `/editor` (кластер редактора лекций, не основная `/admin`).
**Доступ:** `AdminOnly`-подобный гейт панели `editor`:
`isAdminLike() || is_lecture_editor` (см. `User::canAccessPanel`) — то есть
админ-подобные роли **или** пользователь с явным флагом `is_lecture_editor` (отдельная
редакторская роль, не входящая в общий список `Roles`).

- **Phase A** — асинхронный пайплайн: тяжелые операции редактирования уходят в очередь
  вместо блокировки запроса.
- **Phase B** — структурное редактирование: перемещение/удаление/разбиение/слияние
  блоков лекции, вставка нового блока.
- **Phase C** — advisory-лок (предупреждение, если лекцию уже редактирует кто-то
  другой) + откат к бэкапу версии.

**Готча:** advisory-лок не жесткий — он предупреждает, но не блокирует физически
параллельное сохранение; при коллизии используйте откат к бэкапу.

## 4. Прана / геймификация / реферальная программа

**Доступ по умолчанию** ко всем ресурсам этого раздела: ⚪ нет явного `canAccess()`/
`RoleGate::` в коде ресурсов — видны любому пользователю с доступом в панель
(admin/teacher/manager/accountant), кроме случаев, отмеченных отдельно. Сама механика
начисления/траты праны работает в студенческом кабинете — здесь только админ-настройка.

### 4.1. Магазин праны (#207)

**Где:** **Маркетинг → Магазин праны** (`PranaPerkResource`).

Админ определяет «плюшки», которые студент может купить за накопленную прану
(внутреннюю игровую валюту): создание/редактирование позиций магазина (название,
стоимость в пране, описание).

### 4.2. Покупки за прану (журнал)

**Где:** **Маркетинг → Покупки за прану** (`PranaRedemptionResource`).

Журнал того, что студенты уже выкупили в магазине праны (§4.1) — для проверки, кому
что причитается физически выдать (если плюшка не авто-цифровая).

### 4.3. Streak-награды за серию активных дней (#206)

Начисление праны за непрерывную серию активных дней в кабинете — конфигурация серии
(пороги, размер награды) без отдельного крупного UI-экрана; проверить
`MarketingSetting`/связанный enum, если нужно поменять пороги.

### 4.4. Бейджи-достижения (#204) / таблица лидеров (#202)

Геймификационные бейджи и общий рейтинг по накопленной пране — отображаются в
кабинете студента; админ-конфигурация (если есть) — через те же общие настройки.

### 4.5. Two-counter — скидочный кошелек + накопительный ранг (#170)

Прана разделена на два счетчика: «тратибельный» (кошелек на покупки в магазине) и
«накопительный» (ранг/статус, не тратится). Это меняет то, как читать баланс праны
студента в карточке — тратибельная часть может быть меньше общего накопленного ранга.

### 4.6. P2P-перевод и сгорание (decay) праны (#171)

Студенты могут переводить прану друг другу; неактивная прана «сгорает» по расписанию
(`prana:decay`, еженедельно, ночное окно — задача в `schedule()`, не ручной запуск).

**Готча:** decay необратим — если студент жалуется на пропавшую прану, проверить, не
истекло ли окно неактивности до жалобы.

### 4.7. Реферальная программа с наградой праной / денежный кредит вместо праны (#168, #201)

**Где:** конфигурация в **Маркетинг → Глобальные настройки**; нет отдельного
Filament-ресурса «Рефералы» — учет идет через существующие модели пользователя/платежа.

Приглашенный студентом друг дает пригласившему награду. Изначально — прана; позже
добавлена альтернатива — **денежный кредит** (скидка на следующую оплату) вместо
игровой валюты, для тех программ, где прана менее мотивирует.

### 4.8. Партнерская (агентская) программа — денежная выплата за приведенного клиента (H292)

**Где:** **Продажи → Партнеры** (`PartnerResource`; доступ `RoleGate::any(ADMIN, MANAGER)`).
Раздел и публичный лендинг `/partners` видны только при включенном флаге `config('partner.enabled')` (`PARTNER_PROGRAM_ENABLED`, по умолчанию **ВЫКЛ**).

Отдельная от студенческой реферальной (§4.7): **внешний партнер** (не обязательно наш студент) рекомендует курсы и получает **фиксированную денежную выплату** (`PARTNER_REWARD_AMOUNT`, дефолт **1000 ₽**) за каждого приведенного клиента, впервые реально оплатившего курс — не кредит на покупку, а реальная выплата на согласованные реквизиты.

- **Заявки:** партнер регистрируется на `/partners` (или через Telegram-бот) → создается в статусе «На модерации»; бейдж раздела показывает число ожидающих. Кнопка **«Активировать»** выдает код и включает атрибуцию, **«Приостановить»** — отключает привязку новых клиентов.
- **Ссылка:** партнер делится чистой ссылкой `/mitram/<КОД>` (last-touch атрибуция клиента; легаси-форма `?pref=<КОД>` тоже работает).
- **Начисления и выплаты:** вкладка **«Клиенты и выплаты»** в карточке партнера — каждый приведенный клиент с суммой и статусом. Начисление создается автоматически при первой оплате («Начислено / к выплате»); после реальной выплаты нажать **«Отметить выплату»** (accrued → paid_out). Колонки списка: «Клиентов», «К выплате», «Выплачено».
- **Индивидуальная ставка:** в карточке можно задать сумму вместо глобальной.

**Готча:** при откате оплаты клиента (возврат/отмена) еще не выплаченное начисление снимается автоматически; уже отмеченное «Выплачено» — нет (реальные деньги не откатываем, разбирать вручную).

Полная спека, текст приглашения партнерам и API бота — [`docs/partner-program.md`](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/partner-program.md).

## 5. Авторизация, API, разное

### 5.1. VK / Yandex Socialite community-драйверы (#208, scaffold #169)

**Где:** настройка не в `/admin`, а в конфиге приложения (env-ключи провайдеров) —
чисто техническая инфраструктура для входа студентов через VK/Yandex. Нет отдельного
admin-экрана; упомянуто здесь, т.к. может повлиять на карточку студента (появляется
привязанный провайдер входа).

### 5.2. Мобильный API кабинета на Sanctum-токенах (#167)

**Где:** нет UI-экрана — API-эндпоинты для мобильного клиента кабинета студента,
аутентификация через Sanctum-токены. Чисто бэкенд-инфраструктура, упомянута для
полноты списка изменений за месяц.

### 5.3. Дашборд покрытия уроков материалами (суперадмин)

**Где:** `/admin` → «Материалы уроков» (`LessonMaterials`).
**Доступ:** 🔴 только супер-админ (`canAccess()`/`shouldRegisterNavigation()`:
`RoleGate::isSuperAdmin()`).

Показывает, у какой доли уроков есть прикрепленные материалы (конспект/запись/
домашка) — сигнал, где контент еще не наполнен. Виджет `LessonMaterialsStatsWidget`
дает сводные цифры сверху.

### 5.4. Сворачиваемое меню в иконки + зум таблиц

**Где:** глобально по всей панели `/admin` — переключатель в шапке.
**Доступ:** доступен всем ролям с панелью (UI-настройка, не гейт данных).

Боковое меню можно свернуть до иконок (больше места для контента); отдельно — зум
(масштаб) для широких таблиц, чтобы влезало больше колонок на экране без горизонтальной
прокрутки.
