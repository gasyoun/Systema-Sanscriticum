# Приёмка и риски: взаимозачёт и групповые проверяющие

_Created: 27-07-2026 · Last updated: 27-07-2026_

Слой «чем доказано, что работает» для [PLAN_SYSTEMA_TEACHER_STUDENT_SETTLEMENT_GROUP_REVIEWERS_2026H2.md](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/PLAN_SYSTEMA_TEACHER_STUDENT_SETTLEMENT_GROUP_REVIEWERS_2026H2.md).

Планка принята в интервью: автотесты на фикстурах закрывают логику, ручная проверка на боевом закрывает деньги. Тесты идут на SQLite в памяти, боевая база локально недоступна — поэтому ни один критерий ниже не опирается на реальные данные.

---

## Волна A

| Поставка | Критерий готовности | Чем проверяется |
|---|---|---|
| A1 | Грант создаётся, повторный грант той же паре падает на уникальном индексе | `tests/Feature/GroupReviewerTest.php` |
| A2 | Админ выдаёт грант из карточки группы; преподаватель — не может | Тест на политику + ручной проход |
| A3 | Проверяющий видит работы подшефных групп и **не видит** работы других групп того же курса | Тест на выборку с двумя группами одного курса |
| A3 | Проверяющий не видит **собственные** сданные работы | Отдельный тест — дефолт агента, важно, чтобы он был зафиксирован |
| A3 | Ученик из двух групп: работа по чужому курсу не протекает в очередь | Тест с учеником в группах 60 и «хинди-12» |
| A3 | Счётчик у пункта меню равен числу видимых работ в статусе «на проверке» | Тест на бейдж |
| A4 | Виден состав и посещаемость подшефных групп и ничего сверх | Тест на выборку `StudentGroupResource` |
| A4 | Курсы, уроки, расписание, сертификаты, карточки учеников грантом **не** открываются | Негативный тест на каждую поверхность |
| A5 | При сдаче работы проверяющий получает запись в колокольчик, письмо и Telegram | Тест с `Notification::fake()` и `Mail::fake()` |
| A5 | Группа без проверяющих: преподаватель получает письмо как раньше, поведение не изменилось | Регрессионный тест |
| A6 | Дайджест уходит понедельник 09:00, пустой не отправляется | Тест команды с подменой времени |

**Главный регрессионный тест волны A:** выдать проверяющему грант на группы курса, где он не преподаёт, и убедиться, что `TeacherSalaryService::totalForTeacher()` для него не изменился ни на копейку. Именно эта ловушка отвергла путь «добавить со-преподавателем».

## Волна B

| Поставка | Критерий готовности | Чем проверяется |
|---|---|---|
| B1 | Сумма обучения не включает тарифы `Расход` и `salary_payout` | Тест с подмешанными расходными строками |
| B1 | Зарплатная цифра совпадает с той, что выдаёт страница ЗП за тот же период | Тест сверки двух источников |
| B1 | Гард «один человек» падает, если `users.teacher_id` не совпадает | Тест на исключение |
| B2 | `settlement:preview` печатает обе суммы и разницу, ничего не пишет | Тест команды + проверка отсутствия записей |
| B3 | Фиксация замораживает цифры: поздний платёж задним числом не двигает зафиксированную сумму | Тест — фиксируем, добавляем платёж, читаем акт |
| B3 | Повторная фиксация переводит прежний акт в `superseded`, история сохраняется | Тест |
| B4 | Обе суммы с расшифровкой, разница, направление зачёта | Ручная проверка на боевом |
| B5 | Выплата создаётся нетто; `breakdown` содержит `mutual_settlement_id` и сумму зачёта | Тест на создание выплаты |
| B5 | Один акт нельзя зачесть дважды | Тест — повторная попытка зачёта отвергается |
| B6 | Бейдж загорается, когда начисление перевешивает оплаты | Тест на `needsReview()` в обе стороны |

**Главный регрессионный тест волны B:** прогнать существующий набор тестов зарплатной страницы до и после правки B5 — механизмы «прямые платежи» и «зачёт аванса» обязаны считать ровно как считали.

## Ручной чек-лист на боевом (человек)

1. Ольга заходит в админку и видит счётчик у «Домашних работ».
2. В очереди — только работы учеников групп 60 и 61 и только по курсам этих групп.
3. Своих собственных работ она в очереди не видит.
4. Она принимает работу; в карточке проверяющим значится она.
5. Гасунс в понедельник получает недельную сводку.
6. Расчёт зарплаты Гасунса за период не изменился.
7. `settlement:preview` по Ольге печатает обе суммы; они сходятся с ожиданиями.
8. Акт фиксируется, выплата создаётся нетто.

## Риски

| Риск | Насколько вероятно | Что делаем |
|---|---|---|
| Грант через `course_teacher` начислит ЗП с чужой выручки | Высокий, если исполнитель выберет «дешёвый» путь | Путь явно запрещён в плане, закрыт регрессионным тестом |
| Ученик в нескольких группах — протечка чужих работ | Средний | Правило видимости требует совпадения и группы, и курса; отдельный тест |
| Зафиксированная цифра «уплывает» от поздней оплаты | Средний | Фиксация хранит числа, а не пересчитывает; тест на это есть |
| Двойной зачёт одного акта | Средний | Однократность на уровне данных через `payout_id` |
| Первая сверка ждёт доступа к прод-БД | Высокий, уже реализовался в [H165](https://github.com/gasyoun/Uprava/blob/main/handoffs/H165-Sonnet_DO_Systema-Sanscriticum_group_teacher_pace_analytics_04.07.26.md) | Код и тесты не зависят от боевых данных; ждёт только цифра |
| Позиция по НПД не подтвердится у бухгалтера | Средний | Механизм считает и фиксирует зачёт; как оформляется чек — снаружи кода, переигрывается без переписывания |
| Дайджест меняет привычки других преподавателей | Низкий | Замена персональных писем срабатывает только для групп с активным проверяющим |
| `vendor/` через junction в worktree | Средний, известная ловушка репозитория | Свой `composer install` на worktree, никаких junction |

## Что стоит проверить до старта волны B

- Фактический гейт доступа `TeacherSalaries` — ставить такой же, а не выбирать по догадке.
- Проставлен ли `users.teacher_id` у Ольги на боевом.
- Точные `id` групп 60 и 61.
