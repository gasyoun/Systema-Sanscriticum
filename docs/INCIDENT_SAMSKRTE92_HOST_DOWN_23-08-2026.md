## Ранжирование версий

### V1 — хост-событие Proxmox (наиболее вероятно)
Контейнер остановлен/заморожен либо нода деградировала; host-OOM способен
заморозить самого прожорливого гостя. Прямая связь со стоящей дырой: `/tmp`
tmpfs без `size=` = заявка на **половину RAM хоста** (126 ГиБ потолка), и
повторный скретч-шторм как 19-08 бьёт не по контейнеру, а по хосту — ровно ради
этого Артёму просили P5.
- **За**: мгновенность; тотальность (включая ICMP); история 19-08.
- **Против**: `.91` жив → либо разные ноды, либо пострадал один CT.

### V2 — сетевой глюк провайдера / аплинка
- **За**: ничего не требуется от бокса.
- **Против**: обычно самоисцеляется за минуты (уже дольше); первая фаза
  WSAEACCES не характерна (ожидали бы таймауты).

### V3 — nftables-lockout (класс R3 из UPTIME_GUARDRAILS)
Бокс может быть **жив**, но весь трафик зарезан неудачным ruleset волны W4.
Самый коварный вариант: обычный SSH не поможет вовсе.
- **За**: известный класс риска; WSAEACCES на первой фазе странно похож на
  фильтрацию, а не на смерть хоста.
- **Против**: W4 по плану ещё не применялся необратимо; полная тишина ICMP
  редко конфигурируется намеренно.

### Различающие проверки (2 минуты в консоли Proxmox, только Артём)
1. Статус CT: running / stopped / frozen?
2. Uptime ноды; `dmesg -T | grep -iE 'oom|killed process'`
3. Память ноды (free) против суммы гостей.
4. `nft list ruleset` + счётчики drop на хосте и в CT.
5. Если CT stopped — `pct start` и смотреть, выживает ли.

## Связь с P5/P3

Если подтвердится V1 — P5 (`size=` на tmpfs со стороны хоста) перестаёт быть
гигиеной и становится доказанным требованием выживания; заодно поднять вопрос
swap-sizing ноды (P3).
