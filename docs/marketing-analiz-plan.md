# Маркетинг-аналитика samskrte.ru: детальный план (Tier 1–3)

Цель — превратить «что менять на сайте» из догадок в решения на данных. План привязан к тому, что **уже собирается** в платформе (модель `Payment`, модуль `LeadCost`, Яндекс.Метрика + VK-пиксель), поэтому Tier 1 не требует нового сбора — только запросы и проверку целей в Метрике.

Связано с: стратегией [docs/zapisi-katalog-strategiya.md](zapisi-katalog-strategiya.md), issue [#190](https://github.com/gasyoun/Systema-Sanscriticum/issues/190).

---

## 0. Инвентарь данных (что у нас уже есть)

| Источник | Где в коде | Что даёт |
|---|---|---|
| `Payment` | [app/Models/Payment.php](../app/Models/Payment.php) | `landing_page_id`, `course_id`, `tariff` (`full`/`block_N`/`block_N_hH`), `start_block`/`end_block`, `amount`, `promo_code_id`, `discount_*`, `lead_id`, `is_conditional` (рассрочка), `prana_spent`, `status`, `created_at` |
| `Tariff` | [app/Models/Tariff.php](../app/Models/Tariff.php) | тип тарифа, `block_number`/`block_half`, цена/старая цена |
| Модуль LeadCost | [app/Filament/Pages/LeadCost/](../app/Filament/Pages/LeadCost) | расход на рекламу по постам/директу, дашборд, графики — **CAC уже считается** |
| Метрика + VK-пиксель | поля `yandex_metrika_id`, `vk_pixel_id` в `LandingPage` | поведение на лендинге, источники трафика |
| `Lead` | `lead_id` в `Payment` | связка лид → покупка |
| Prana (баллы лояльности) | `prana_spent` в `Payment` | вовлечение/возвраты через бонусы |

**Вывод:** attach-rate, выручка-по-лендингу, LTV, промокоды, рассрочка — всё считается из `Payment` без доработок. Воронка и CAC — из Метрики и LeadCost.

## Tier 1 — на своих данных, делаем первыми

Формат карточки: **что считаем → источник → метод → что решает → усилие**.

### A1. Воронка конверсии
- **Что:** доля переходов лендинг → витрина `/online/kursy/{slug}` → `checkout` → оплаченный `Payment(status=paid)`. Главный обрыв.
- **Источник:** Метрика (цели по шагам) + `Payment.status`.
- **Метод:** настроить **цели** в Метрике на 3 события (клик «Купить запись», открытие checkout, успешная оплата); снять воронку по каждому лендингу.
- **Решает:** что именно чинить на странице (если рвётся на лендинг→витрина — слабый оффер/CTA; если checkout→оплата — сложная/недоверчивая оплата).
- **Усилие:** S (если цели уже есть) / M (если ставить). ⚠️ Предусловие — см. §1.

### A2. CAC и окупаемость по каналам
- **Что:** стоимость лида и стоимость покупки по источникам; ROMI канала.
- **Источник:** модуль **LeadCost** (расход) + `Payment.amount` с привязкой к `lead_id`/источнику.
- **Метод:** использовать готовый [LeadCostDashboard](../app/Filament/Pages/LeadCost); сопоставить расход канала с выручкой привлечённых им покупок.
- **Решает:** куда лить бюджет, какой канал отключить.
- **Усилие:** S (дашборд есть; нужна корректная разметка источника лида).

### A3. Attach-rate «блок vs весь курс»
- **Что:** % покупок `full` против `block_*`; средний размер блочной покупки (`end_block − start_block`); сколько блочных потом добирают до полного.
- **Источник:** `Payment.tariff`, `start_block`, `end_block`, `course_id`, `user_id`.
- **Метод:** группировка по `tariff`-префиксу; для добора — есть ли у одного `user_id`+`course_id` несколько блочных платежей или блок→full.
- **Решает:** правильно ли устроено дробление (наша ключевая фишка из стратегии), нужен ли апселл «доплати до полного», верны ли цены блока.
- **Усилие:** S (один SQL по `Payment`).

### A4. LTV и повторные покупки (когорты)
- **Что:** сколько курсов покупает один ученик; доля вернувшихся за вторым; LTV по когортам (месяц первой покупки).
- **Источник:** `Payment` группировкой по `user_id`, `created_at`.
- **Метод:** когортная таблица «месяц первой покупки × число последующих покупок».
- **Решает:** **главный аргумент за/против подписки на каталог** — если повторных мало, сначала растить каталог и тему-навигацию, а не запускать подписку.
- **Усилие:** M.

### A5. Брошенный checkout и рассрочка
- **Что:** сколько доходит до `checkout` и не оплачивает; доля `is_conditional` (рассрочка/обещание); конверсия рассрочки в полную оплату.
- **Источник:** `Payment(status=pending vs paid)`, `is_conditional`, `deposit_consumed_at`.
- **Метод:** доля pending→paid; срез по наличию рассрочки.
- **Решает:** нужны ли триггерные письма о брошенной оплате, заметнее ли показывать рассрочку, упрощать ли шаг оплаты.
- **Усилие:** S.

## Tier 2 — внешние данные, небольшой сбор

### A6. Анализ спроса (Wordstat / поиск)
- **Что:** частотность запросов «санскрит курс», «джьотиша онлайн», «бхагавад-гита разбор», «индийская философия» и т. п.
- **Источник:** Яндекс.Wordstat, подсказки, Метрика — поисковые фразы.
- **Решает:** какие темы записывать/доснимать, под какие делать SEO-лендинги, как называть курсы.
- **Усилие:** M.

### A7. Прайс-бенчмарк
- **Что:** наши цены (курс/блок) против Нитки, Синхронизации, Arzamas (частично собрано в стратегии).
- **Источник:** страницы курсов конкурентов + наша таблица тарифов.
- **Решает:** позиционирование — премиум (как Нитка) или объём/подписка (как Arzamas).
- **Усилие:** S.

### A8. Gap-анализ каталога
- **Что:** предметные оси Arzamas/Синхронизации vs наш каталог — какие темы у них есть, у нас нет.
- **Источник:** каталоги конкурентов + наш список `Course`.
- **Решает:** план записи новых курсов; структура навигации по предмету.
- **Усилие:** M.

### A9. Эффективность промокодов и скидок
- **Что:** какие промокоды двигают продажи, влияние `discount_percent` на конверсию и средний чек.
- **Источник:** `Payment.promo_code_id`, `discount_percent`, `discount_amount`.
- **Метод:** выручка/число покупок в разрезе промокода; «скидка vs итоговая выручка».
- **Решает:** скидочная политика, стоит ли механика −30 % за email (как у Синхронизации).
- **Усилие:** S.

## Tier 3 — опросы и эксперименты

### A10. JTBD / сегментация аудитории
- **Что:** кто покупает и зачем — новичок-любитель / практик / академ.
- **Источник:** опрос из 5 вопросов после покупки (или письмом по базе).
- **Решает:** тон лендингов, какие форматы (запись / живой / интенсив как у Нитки), как сегментировать каталог.
- **Усилие:** M (составить + разослать + разобрать).

### A11. Email-захват вместо «заявки»
- **Что:** конверсия lead-magnet → покупка; тест механики «email за −30 % на первую покупку».
- **Источник:** `Lead`, lead-magnet поля `LandingPage`, последующие `Payment` по `lead_id`.
- **Решает:** заменить «оставить заявку» на цивилизованный email-захват с офертой (модель Синхронизации).
- **Усилие:** M.

### A12. A/B-тесты на лендингах
- **Что:** формулировка CTA, ценовой якорь (старая/новая цена), оффер «Купить запись» vs «Лист ожидания».
- **Источник:** Метрика-эксперименты / разметка вариантов лендинга.
- **Решает:** какие тексты и офферы конвертят лучше.
- **Усилие:** M, итеративно.

## 1. Предусловия по инструментации (чтобы Tier 1 заработал точно)

Прежде чем снимать воронку и CAC, проверить/доставить:

1. **Цели в Метрике** на 3 ключевых шага: клик «Купить запись», открытие `checkout`, успешная оплата (`thankyou`/`status=paid`). Без них A1 неполна.
2. **Сквозная разметка источника лида** (UTM → `Lead`/`Payment`), иначе A2 (CAC по каналам) считается грубо.
3. **Различение `status`** в `Payment` (`pending`/`paid`/возврат) — нужно для A5.

Это полдня работы и разблокирует весь Tier 1.
