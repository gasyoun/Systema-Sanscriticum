## 1. The five-layer model

Every guardrail in this plan belongs to exactly one layer. The layers are ordered by how late
they fire; **a failure that reaches layer 5 has already cost the bar**.

| # | Layer | Fires when | Existing on `.92` | Existing on `.91` |
|---|---|---|---|---|
| 1 | **Bound** — a resource cannot grow past a ceiling | before anything is wrong | cgroup caps, `memory_limit`, `TasksMax`, `pm.max_children` | none |
| 2 | **Shed** — something is killed while the OS can still act | pressure, pre-livelock | `earlyoom` | none |
| 3 | **Serialize** — work cannot pile up on itself | concurrency | `flock -n`, `timeout`, stale-lock reclaim | Docker `restart: unless-stopped` only |
| 4 | **Observe** — the state is recorded and asserted | continuously | `memwatch`, `sysstat`, `guards:verify`, `cabinet:probe` | journald only |
| 5 | **Escalate** — a human or a remediator is told | after failure | Better Stack, Telegram, auto-deploy breaker | **nothing** |

The audit's shape in one line: `.92` has all five and gained new layer-1/4 coverage after
H3121; `.91` has a weak layer 3 and nothing else. Wave 2 builds layers 1–4 on `.91`; Wave 3
builds layer 5 for both.

### 1.1 The invariant this architecture is organised around

> **A guard must not share a fate with what it guards.**

Learned expensively on 28-07-2026, when `cabinet:probe` lived inside the `schedule:run` that
hung, so the site's death went unreported for 79 minutes
([server-resource-guards.md §3](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/server-resource-guards.md)).
It is why `.92`'s watchdogs are separate cron lines, why D7 chose reciprocal cross-host
probes over a single in-box checker, and why Better Stack silence — a signal generated by
*absence*, outside both boxes — remains the only mechanism that survives total container
death.

Applied to each new component below as an explicit column: **whose fate does it share?**

## 3. Contracts

### 3.1 The guard-row contract (extends the existing one)

Every guardrail — old or new, either box — is a row in a `manifest.psv` with the shape
`source | destination | mode | owner`, values interpolated from a single `.conf`, applied
idempotently, and asserted by a verify command. This contract already exists on `.92`; the
plan's only change is that **`.91` gets its own manifest under the same rules**, and that the
verify command learns three new check kinds:

| Check kind | Asserts | Severity when violated |
|---|---|---|
| `tmpfs-cap` | `/tmp` is mounted with an explicit `size=` at or below the configured ceiling | **critical** — an uncapped `/tmp` is an unbounded RAM claim |
| `failed-units` | `systemctl --failed` is empty | **warning** — a permanently-failed unit is a dead guard (H-2) |
| `backup-fresh` | an archive newer than `BACKUP_MAX_AGE_DAYS` exists **at the offsite destination** | **critical** — a local-only backup is not a backup |
| `peer-reachable` | the other box answered the cross-probe within the grace window | **warning** on `.92`, **critical** on `.91` |

Severity follows the existing soft/critical model in
[SERVER_SOFT_ALERT_PLAYBOOK.md](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/docs/SERVER_SOFT_ALERT_PLAYBOOK.md) —
soft goes to Telegram with a cooldown, critical additionally drives the heartbeat `/fail`.

### 3.2 The heartbeat contract (unchanged, reused verbatim)

```text
POST https://uptime.betterstack.com/api/v1/heartbeat/<TOKEN>        # success
POST https://uptime.betterstack.com/api/v1/heartbeat/<TOKEN>/fail   # explicit fail
```

Tokens live only in prod `.env` or `/etc/default/*` and are **never** committed. Docs name
env **keys**. `.91` adds `N8N_HEARTBEAT_URL` and `PEER_PROBE_HEARTBEAT_URL`; `.92` adds
`PEER_PROBE_HEARTBEAT_URL`. No change to the app-side contract — this is deliberate reuse.

### 3.3 The remediation-ladder contract (new, D8/D9)

Four rungs, each requiring the previous to have failed, each logging before acting:

| Rung | Action | Authority | Gate |
|---|---|---|---|
| R1 | Log + record in the incident ledger | always | — |
| R2 | `systemctl restart <unit>` / `docker restart <container>` | automatic | unit/container is the *only* thing unhealthy; smoke recovers within 60 s or escalate |
| R3 | Clear aged `/tmp` scratch past the age rule | automatic | age rule only; never a path outside `/tmp` |
| R4 | Restart the LXC container via Proxmox API | **inert until `PROXMOX_API_TOKEN` exists** | absent the token: log `would restart <ct>` + Telegram escalation |

R4's inertness is the whole of D9 and it is load-bearing: the lane is written, tested against
a stubbed API, and shipped disabled. Activation is one env line, not a code change. **An agent
must never work around a missing token by inventing a host access path** — that is a D4
violation and P1's whole purpose.

### 3.4 The incident-ledger contract (new, D14)

One row per event, appended, never rewritten:

| Field | Meaning |
|---|---|
| `class` | one of: oom · throttle · hang · disk · network · deploy · third-party |
| `detected_at` | first machine signal, whatever produced it |
| `notified_at` | first message that reached a human |
| `recovered_at` | first green smoke after |
| `mttd` / `mttr` | derived, not entered |
| `guard` | which guard caught it, or `none` — the column that says whether the span is working |

A `guard = none` row is the most valuable row in the file: it names a failure class nothing
was watching, which is precisely how H3121 was found.

## 4. Build vs reuse — verdict per piece

Prior-art check run 19-08-2026 across the repo, `hub_grep`, and both live hosts.

| Piece | Verdict | Why |
|---|---|---|
| Guard manifest + applier | **Reuse** [server_guards_apply.sh](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/scripts/server_guards_apply.sh) | Idempotent, backs up to `/root/preflight-backup-<stamp>/`, proven across four incidents. Parameterise for a second manifest; do not fork |
| `guards:verify` | **Extend** [VerifyServerGuards.php](https://github.com/gasyoun/Systema-Sanscriticum/blob/main/app/Console/Commands/VerifyServerGuards.php) | Already carries severity, Telegram routing, and the `cabinet_probe_runs` trail. Add the four check kinds of §3.1 |
| `earlyoom` config | **Reuse the pattern**, new thresholds | `.91`'s avoid/prefer lists differ (Docker, not PHP) but the reasoning in the `.92` file transfers verbatim |
| Cross-host probe script | **Reuse the template** `cologne-cdsl-heartbeat.sh` | Same shape: curl → keyword → heartbeat or `/fail`. Already proven against two third-party targets |
| Better Stack wiring | **Reuse the account and contract** | D3 free tier; team `t576984` already holds 5 monitors |
| Backup machinery | **Reuse** Spatie `backup:run`/`:clean`/`:monitor` | The tool is fine; W1c fixes *delivery and alerting*, not the tool. `.91`'s sqlite dump is a small shell script, not a second framework |
| Docker limits/healthchecks | **Build** (small) | Nothing exists; it is ~20 lines of `docker-compose.yml` |
| Incident ledger | **Build** (small) | No equivalent exists. `server-resource-guards.md` narrates incidents in prose but yields no MTTD/MTTR |
| tmpfs cap | **Build** (small) | A `tmpfs.mount` drop-in + `tmpfiles.d` rule per box |
| Remediation ladder | **Build**, reusing `ops:soft-remediate`'s safety philosophy | Existing remediation is deploy-breaker-specific; the ladder generalises it |

**Nothing here rebuilds an existing asset.** The two genuinely new components (incident ledger,
remediation ladder) were checked against `hub_grep` and the org hubs and have no owner.

## 5. Failure classes and which layer covers each

The point of the table: a class with no layer is a future seven-hour outage.

| Class | Example | Covered by | Gap after this plan |
|---|---|---|---|
| Memory exhaustion | 24-07, 28-07 `.92` | L1 caps + L2 `earlyoom` | closed both boxes after W2 |
| **cgroup throttling** | 18→19-08 `.92` (H3121) | L4 `guards:verify` `cgroup` check | closed on `.92`; W2 ports it |
| **tmpfs RAM claim** | H-1, live now, both boxes | **nothing today** → W1a/W2a L1 | closed |
| Scheduler pile-up | 28-07 `.92` | L3 `flock` + `timeout` | closed; `.91` has no scheduler |
| Container hang (guest alive, unresponsive) | 24-07 `.92` | L5 Better Stack silence + R4 | **detection closed; automatic recovery waits on P1** |
| Host/Proxmox failure | both boxes at once | L5 silence only | **out of scope by D4** — Artem |
| Dead guard | H-2, live now | `failed-units` check (W1b) | closed |
| Data loss | H-3, live now | offsite + freshness (W1c/W2c) | closed after restore drill |
| Disk exhaustion | none observed (16 %/23 %) | L4 only | **acknowledged gap** — no alert threshold today; added in W2a |
| Brute-force / flood | none observed | fail2ban on `.92` only | closed on `.91` in W4 |

Two rows are deliberately left open and named as such: **host failure** (D4) and **automatic**
container recovery (P1). Both have detection; neither has agent-side remediation, and the plan
says so rather than implying coverage.

## 6. What this architecture deliberately does not do

- **No agent.** No Prometheus/Grafana/node_exporter stack. D3's free-tier ruling and the
  existing `memwatch` + `sysstat` + Better Stack combination already answer "what happened",
  and a metrics stack is one more daemon to guard on a box that is short of RAM.
- **No config-management framework.** Ansible/Salt would replace a working, auditable, 300-line
  applier with a dependency. D6 keeps the existing pattern.
- **No second alerting vendor.** One silence-based provider plus Telegram detail is enough for
  a 15-minute bar; two would double the false-positive surface.
